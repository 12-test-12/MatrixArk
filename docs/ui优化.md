# MatrixArk 发布账号管理页面 2.0 — UI/UX 与交互重构实施提示词

## 1. 项目背景

项目：MatrixArk

GitHub：https://github.com/12-test-12/MatrixArk

本次任务针对「发布账号与矩阵组」页面进行一次系统性优化。

当前页面已经具备：

- 多平台账号接入。
- B站、小红书扫码接入。
- 账号密码与 Cookie 导入。
- 矩阵组管理。
- 账号批量分组。
- 批量分配运营负责人。
- 账号风险管理。
- 环境体检。
- 读写账号分离。
- 账号主页链接编辑（B 站 UID / space 链接，小红书 24 位 ID / 主页链接；小红书 Cookie 导入可自动识别主页链接）。
- 账号归档与恢复。
- 账号成效查看。
- 账号置顶。

因此，本次不需要重新开发这些已有功能；托管凭据按「只写不读」处理（详见第 10 节）。

## 1.1 现状基线（实现前先以此为准）

- **托管凭据只写不读**：`GET /accounts/:id/credentials` 已下线，页面没有明文查看或复制入口；密码与 Cookie 只在写入时加密保存。
- **账号主页链接可编辑**：`profileUrl` 已随列表返回；B 站支持数字 UID / `space.bilibili.com` 链接，小红书支持 24 位 ID / `www.xiaohongshu.com/user/profile/...` 链接（Cookie 导入时可从 `x-user-id-creator.xiaohongshu.com` 自动识别），非法输入返回 400。
- **列表接口（`GET /accounts`）当前下发**：`identityVerified`、`identityCheckedAt`、`availableForHandoff`、`availableForOfficial`、`riskStatus`、`riskReason`、环境字段、分组、置顶、`profileUrl`、`hasPassword` / `hasCookie` / `hasReadCookie` 等。**没有**下发 `externalId` / `platformUid`、`authStatus`、`authExpiresAt`、`authCheckedAt`、`availableForMetrics`，也没有业务能力不可用的原因。
- **矩阵组统计**（`accountCount` / `availableCount` / `riskCount`）由 `GET /accounts/groups` 每次请求实时计算，不是数据库字段；只统计未归档账号。
- **测试基建**：`apps/web` 没有测试脚本或测试框架；能执行的是 `tsc`、`next build` 和 API 侧 `node --test`。
- **列表不分页**：`GET /accounts` 一次返回全部（置顶优先、创建时间升序）。本期按 100 个账号以内全量渲染设计，更大规模的分页/虚拟滚动不在范围内。

本次的核心任务是：

**在不破坏现有业务逻辑的前提下，将目前的账号管理页面升级为适合管理 100 个甚至更多账号的专业化账号运营中心。**

重点解决：

1. 账号信息展示混乱。
2. 账号状态语义不清晰。
3. 每行操作按钮过多。
4. 详情采用行内展开，导致页面越来越长。
5. 缺少高效的账号筛选和定位能力。
6. 账号批量管理体验不够完善。
7. 矩阵组数量增加后，页面管理效率下降。

# 3. 核心改造一：重新设计账号状态体系

这是本次最重要的改造。

当前代码中：

`accountStatus(account, archived)`

负责判断账号的业务状态。

`riskBadge(status)`

负责展示风险状态。

目前这两套状态在界面上容易产生误解。

例如：

一个账号可能显示：

- 未核验
- 健康正常

这两个状态实际上可以同时成立，但用户容易误认为系统出现了判断冲突。

## 3.1 拆分四个独立维度

每个账号必须明确展示以下信息。

### A. 身份状态

依据现有 `identityVerified` 判断：

- 已核验。
- 待核验。

### B. 业务能力

依据现有字段：

- `availableForOfficial`
- `availableForHandoff`
- `availableForMetrics`（后端 `resolveAccountCapabilities` 已经计算，当前列表接口没有下发，需要补）
- `channelKind`

展示：

- 官方自动投稿。
- 可人工交接。
- 支持成效读取。
- 沙箱模拟。
- 当前不可用。

一个账号可以具有不同业务能力，不能将业务能力简单等同于授权状态。

「当前不可用」的原因必须由服务端给出原因码，前端只做文案映射，不要在 `accounts.tsx` 里复刻 `resolveAccountCapabilities` 的判断。建议原因码：

- `missing_external_id`：未登记平台 UID。
- `auth_unverified`：待核验。
- `rate_limited`：平台限流。
- `platform_policy`：平台不支持该能力。
- `trial_restricted`：试用工作室限制。

原因码由 `account-capabilities.ts` 生成、随列表接口下发，不新增数据库字段。

### C. 风险状态

依据 `riskStatus` 判断：

- normal：暂无风险记录。
- warning：预警提醒。
- risk：风险异常。

特别注意：

`riskStatus = normal` 不代表账号刚刚完成体检，也不代表登录态一定有效。

如果账号从未进行过环境体检，应当明确显示：

「尚未执行环境体检」。

不能将没有风险记录直接显示为「账号健康正常」。行内当前的绿色「健康正常」必须改掉：没有风险记录时显示「暂无风险记录」，`envCheckedAt` 为空时同时显示「未体检」。体检时间与「尚未执行主动环境体检」的说明在体检抽屉里已经存在，不要重复造数据。

### D. 环境状态

依据：

- `cookieExpiresAt`
- `envCheckedAt`
- `egressIpCollision`
- `readWriteSeparated`
- 环境体检返回的 diagnostics

展示：

- Cookie 到期时间。
- 最近体检时间。
- 出口 IP 冲突。
- 是否启用读写分离。

不要仅凭 Cookie 存在就认定账号登录有效。

## 3.2 状态展示设计

每个账号使用分组状态标签：

身份：已核验

业务：官方自动投稿

风险：暂无风险记录

环境：最近体检时间

不要将这些状态合并成一个绿色的「正常」。

## 3.3 列表接口需要补的非敏感字段

`GET /accounts` 现在只下发身份与能力的 4 个字段。下面这些字段需要补，并同步更新 `apps/web/app/api.ts` 的 `Account` 类型：

- `platformUid`：展示与搜索用的平台 UID（B 站数字 UID / 小红书 24 位 ID）。服务端从 `externalId` 派生，B 站必须去掉 `manual-bili-uid:` / `bili-web-uid:` 前缀；不要把原始 `externalId` 直接展示给用户。
- `authStatus`、`authExpiresAt`、`authCheckedAt`：授权状态与时间。注意 `identityCheckedAt` 是能力判定后的派生值（密码托管、试用、未核验 B 站账号都会返回 null），不能当原始授权时间用。
- `availableForMetrics` 与 3.1 节 B 的原因码。
- `createdAt`：Tab 1 的创建时间。接口已经返回，但 `Account` 类型没有声明，需要同步。

这些都是非敏感字段。禁止将 accessToken、Cookie、密码等凭据加入列表接口；凭据读取接口已经下线，本期也不重新引入（详见第 10 节）。

# 4. 核心改造二：重新设计账号列表

当前 `AccountRow` 采用 Flex 布局，操作区固定在最右；每行最多同时出现环境体检、配置、风险上报、主页、成效、归档 6 个按钮（凭据入口已下线）。

随着账号数量增加，操作区域容易拥挤。

需要重新设计账号行。

## 4.1 桌面端布局

采用 CSS Grid，建议划分为：

| 区域     | 内容                        |
| -------- | --------------------------- |
| 选择区域 | 勾选、置顶                  |
| 账号身份 | 平台图标、名称、UID、负责人 |
| 接入信息 | 扫码、Cookie、OAuth 等      |
| 状态区域 | 身份、业务能力、风险        |
| 操作区域 | 详情、体检、更多            |

参考布局：

```text
┌────────────────────────────────────────────────────────────────────┐
│ □ ☆  [平台] 账号名称                     身份       业务能力       │
│             UID / 负责人 / 标签          已核验     官方自动投稿   │
│             接入方式 / 所属矩阵组         暂无风险记录             │
│                                                                    │
│                                  [账号详情] [环境体检] [更多 ⋯]   │
└────────────────────────────────────────────────────────────────────┘
```

要求：

- 统一账号行高度和间距。
- 账号名称作为视觉重点。
- UID 和负责人作为辅助信息。
- 状态区域不能挤压账号名称。
- 操作区域固定在右侧。
- 支持长名称和长标签换行。
- 不允许内容溢出。
- 不要使用大量颜色区分普通信息。

## 4.2 移动端布局

移动端改为卡片式结构。

账号名称和状态放在第一行。

账号信息放在第二行。

操作按钮放在第三行。

不能简单地将桌面端强行压缩到手机宽度。

# 5. 核心改造三：精简账号操作入口

目前每个账号最多同时展示：

- 环境体检。
- 配置。
- 风险上报。
- 主页（有 `profileUrl` 时）。
- 成效。
- 归档。

托管凭据已经没有查看入口（只写不读），不要为本期新增。

这些入口不应该全部同时出现。

改为三个主要入口。

### 主要入口一：账号详情

打开右侧详情抽屉。

### 主要入口二：环境体检

保留当前真实的联网体检功能。

点击后显示加载状态、体检结果和异常原因。

### 主要入口三：更多操作

使用下拉菜单或其他轻量菜单。

包含：

- 编辑账号配置（含主页链接）。
- 风险上报（已上报时为处理/解除）。
- 查看平台主页。
- 查看作品成效。
- 归档账号。

根据账号权限和平台能力决定具体菜单项。

禁止显示没有实际执行能力的按钮。

菜单需要支持键盘操作，并在点击外部区域时正确关闭。

# 6. 核心改造四：增加独立账号详情抽屉

当前 `AccountRow` 内部通过：

`panel = health | meta | risk`

实现行内展开（凭据面板已随「只写不读」下线）。

这种方式会导致多个账号同时展开时，列表高度大幅增加。

本次建议将账号详情改成统一的右侧抽屉。

建议新增：

`AccountDetailsDrawer`

可以先放在 `accounts.tsx`，如果组件复杂度过高，再独立拆分文件。

## 6.1 抽屉结构

分成五个区域。

### Tab 1：账号概览

展示：

- 平台图标。
- 平台原始昵称。
- 内部别名。
- UID（需要列表补 `platformUid`）。
- 平台主页链接（`profileUrl`，缺失时可在这里补填）。
- 所属矩阵组。
- 运营负责人。
- 标签。
- 创建时间。

### Tab 2：授权与接入

展示：

- 接入方式。
- 身份核验状态（`identityVerified` / `identityCheckedAt`，注意它是能力派生值）。
- 授权状态与到期时间（列表补 `authStatus` / `authExpiresAt` 后展示）。
- Cookie 更新时间与到期时间（已有 `cookieUpdatedAt` / `cookieExpiresAt`）。
- 凭据托管状态：只显示「已托管密码」「已托管 Cookie」「已保存只读 Cookie」和更新时间，不提供明文、不提供复制。

### Tab 3：业务能力

展示：

- 是否可以官方自动投稿。
- 是否可以人工交接。
- 是否支持成效读取（`availableForMetrics`）。
- 是否为沙箱账号。
- 当前不能执行某项业务的原因（服务端原因码 + 前端文案）。

`resolveAccountCapabilities` 在服务端，前端调不到；不要在前端重复编写一套与后端不同的判断逻辑。需要的布尔值与原因码由列表接口下发（见 3.3）。

### Tab 4：运行环境

展示：

- 出口 IP。
- IP 冲突情况。
- 环境槽位标签。
- 是否启用读写分离。
- 绑定的辅助采集账号。
- 独立只读 Cookie 是否存在。
- 最近体检时间。

### Tab 5：风险与事件

复用现有：

`GET /accounts/risks?accountId=xxx`

展示：

- 风险级别。
- 风险类型。
- 发生时间。
- 风险原因。
- 是否已经解除。
- 飞书通知状态。
- 处理人。

没有真实操作审计数据时，不得伪造操作历史。

## 6.2 抽屉交互要求

- 点击账号名称或详情按钮打开。
- 点击关闭按钮关闭。
- 支持 ESC 关闭。
- 点击遮罩层关闭。
- 打开其他账号时切换内容。
- 抽屉内部支持独立滚动。
- 桌面端从右侧滑出。
- 移动端使用接近全屏的抽屉。

一次只能打开一个账号详情。

不要让多个 AccountRow 同时展开详情。

# 7. 核心改造五：账号筛选能力

目前已经存在：

- 按平台筛选（含「全部平台」）。
- 风险筛选（KPI 胶囊：全部 / 正常 / 预警 / 异常）。
- 搜索（账号名、备注、负责人、矩阵组名、标签，前端过滤）。
- 已归档账号查看。
- 按矩阵组 / 按平台两种**视图模式**。

注意：「按矩阵组」是分组展示，不是过滤条件；目前没有「只看某个矩阵组」的筛选。新增组筛选时不要把它和视图模式混在一起。

这些功能必须保留。

不要重新开发已有功能。

在此基础上增加高级筛选。

## 7.1 新增筛选条件

| 筛选维度   | 选项                                    |
| ---------- | --------------------------------------- |
| 身份状态   | 已核验、待核验                          |
| 接入方式   | 扫码、Cookie、账号密码、OAuth、UID 登记、沙箱 |
| 业务能力   | 官方投稿、人工交接、不可用              |
| 风险状态   | 暂无风险记录、预警、异常                |
| 环境状态   | 已体检、未体检                          |
| 运营负责人 | 根据当前账号负责人筛选                  |
| 矩阵组     | 按矩阵组筛选（与「按矩阵组视图」区分）  |

不要一次性把所有筛选项全部展开。

采用「基础筛选 + 高级筛选」形式。

基础区域保留平台、风险状态、矩阵组筛选和搜索；矩阵组筛选项是新能力，必须和现有的「按矩阵组视图」区分开。

高级筛选通过按钮展开。

## 7.2 搜索能力

现有搜索（前端过滤）：

- displayName
- alias
- operator
- group.name
- tags

建议扩展：

- loginIdentifier（列表返回的是脱敏值，只能按脱敏值搜索）。
- 平台 UID（需要先在列表接口补出 `platformUid`，由 `externalId` 派生，属于公开信息）。

搜索逻辑应支持：

- 大小写不敏感。
- 中文模糊匹配。
- 标签匹配。
- 负责人匹配。

不要搜索或展示完整 Cookie、密码、Token。

## 7.3 筛选结果

增加：

- 当前筛选结果数量。
- 清空筛选条件。
- 没有匹配账号时的空状态。
- 保留当前视图模式。

# 8. 核心改造六：完善矩阵组管理

当前已经支持：

- 新建矩阵组。
- 编辑矩阵组。
- 删除矩阵组。
- 账号单一分组。
- 批量移动账号。

这些功能保留。

本次重点优化分组展示。

### 8.1 支持折叠

每个矩阵组增加折叠按钮。

折叠状态下展示：

- 组名称。
- 账号总数。
- 风险账号数量。
- 可用账号数量。

展开后显示账号列表。

### 8.2 优化未分组区域

当未分组账号数量为 0 时：

- 默认折叠或使用紧凑空状态。
- 不占据大块垂直空间。
- 仍然允许用户主动展开。

当有未分组账号时正常展示。

### 8.3 分组统计

`GET /accounts/groups` 返回的统计是**按请求实时计算**的响应字段，不是数据库列，只统计未归档账号：

- `accountCount`：组内账号总数。
- `availableCount`：`resolveAccountCapabilities(...).channel` 有值的账号数。
- `riskCount`：`riskStatus !== 'normal'` 的账号数（预警 + 异常）。

展示规则必须固定，避免组头和列表对不上：

- 未筛选时：组头显示 `accountCount`，与列表行数一致。
- 筛选时：组头继续显示 `accountCount` 等总览值，并额外标注「筛选中 · 匹配 N 个」；不要用过滤后的 `items.length` 冒充总账号数。
- 要调整统计口径时先改后端，不要在前端另算一套。

# 9. 核心改造七：完善批量管理

当前已经实现：

- 批量选择。
- 批量设置矩阵组。
- 批量移出矩阵组。
- 批量分配负责人。

保留现有 `POST /accounts/batch`。

优化交互：

1. 勾选账号后，出现固定的批量操作工具栏。
2. 显示已选数量。
3. 支持选择当前筛选结果。
4. 支持取消选择。
5. 支持批量修改矩阵组。
6. 支持批量修改负责人。
7. 操作完成后正确刷新账号列表。
8. 失败时显示具体原因。

不要为了扩充批量操作而引入未经设计的批量 Cookie 修改、批量重新授权等高风险功能。

当前批量接口是「全成功或整体失败」：只要有一个勾选账号不属于当前工作室，整次操作报错（`部分勾选账号不存在或不属于当前工作室`），不存在部分跳过。如果以后要支持部分跳过，需要单独改后端返回结构；本期不做。

# 10. 核心改造八：凭据边界（只写不读）

现状：托管凭据只能写入，不能读取。

- `GET /accounts/:id/credentials` 已下线，服务端不再解密回传账号密码或 Cookie。
- 页面没有明文查看、复制入口，`AccountRow` 也不再请求凭据。
- 密码与 Cookie 仍按现有算法加密存储，供后台自动投稿与人工交接流程在服务端内部使用。

本期要求：

1. 账号详情只展示凭据的存在性与元数据：`hasPassword`、`hasCookie`、`cookieUpdatedAt`、`cookieExpiresAt`、`hasReadCookie`、`readCookieUpdatedAt`、`readCookieLabel`。
2. 不新增任何「查看明文 / 复制密码 / 复制 Cookie」按钮或快捷键。
3. 不在 localStorage、sessionStorage、URL、控制台、错误日志里出现凭据；前端也不缓存凭据。
4. 列表与详情接口只返回布尔值与时间，明确不下发 `passwordCiphertext`、`cookieCiphertext`、`readCookieCiphertext`。
5. 凭据读取审计（`AccountCredentialAccessEvent` / `AccountAuditEvent`）本期不做：没有可读取的接口，就没有可审计的读取动作。若以后要恢复查看能力，必须单独设计（二次确认、`Cache-Control: no-store`、审计事件），不要夹在 UI 改造里。

更换或重新导入 Cookie 沿用现有写入路径（账号密码托管、Cookie 导入、扫码），不在详情抽屉里做明文回显。
