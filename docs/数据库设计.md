# MatrixArk 数据库设计 v1.3

> 首版数据库和迁移以 PostgreSQL 16 为目标。实施验收见第 8 节。
> SQL 沿用现有 Prisma 的表名、列名和 ID 类型。现有模型的 ID 以及引用它们的新外键均使用 PostgreSQL `text`。
> 依据 [项目底座 v1.1](../PROJECT_FOUNDATION.md)、[技术设计 v1.3](./技术设计.md) 和 [功能与接口设计 v1.3](./功能与接口设计.md)。

## 0. 先给结论

保留现有 11 张表，新增 6 张业务表和 1 张可选缓存表。

| 新增表 | 解决的问题 | 阶段 |
|---|---|---|
| `VariantAsset` | 版本锁图片顺序和封面，换图必须产生新版本 | 首版 · 人工闭环 |
| `VariantRejection` | 审核退回记录，保留退回人、时间和原因 | 首版 · 人工闭环 |
| `TaskEvent` | 任务全生命周期只追加审计，改期/核对/更正可追溯 | 首版 · 任务事务 |
| `NotificationSetting` | 工作室级飞书配置，密文保存 webhook 和签名密钥 | 首版 · 飞书提醒 |
| `PlatformAppSetting` | 按工作室与平台保存应用 ID、加密后的应用密钥和最后更新人 | 首版 · 发布账号接入 |
| `NotificationDelivery` | 飞书投递去重、重试和失败原因 | 首版 · 飞书提醒 |
| `OAuthState` | B 站授权一次性 state，防重放 | 首版 · 官方通道 |
| `PlatformMediaRef` | B 站图片上传结果缓存，按账号复用平台 URL | 可选 · 官方通道 |

现有表的关键改动：

- `Manuscript`、`ChannelAccount` 增加 `archivedAt`，删除改为归档。
- `Asset` 增加 `taskId`、`kind`、`checksum` 和文件校验约束，原稿图与任务截图共用上传规则。
- `Variant` 增加 `platformFields`、`generationSource`、`snapshotVersion` 和 `sealedAt`。版本和图片在创建事务内一起封存，换图时创建新版本。
- `Approval` 增加 `snapshotHash`，确认绑定具体快照；历史审批没有快照时留 `NULL`，强制重审。
- `ChannelAccount` 增加授权状态、授权范围、有效期、限流状态和凭据密文列。
- `PublishTask` 增加 `variantContentHash`、`executionChannel`、`leaseId`、`leaseExpiresAt`；幂等键去掉时间输入。
- `PublishResult` 独立保存已受理到终结的当前回执，增加 `workspaceId`、`evidenceAssetId` 和 `platformPublishedAt`。旧截图经过归属核对、回填和兼容期后再清理旧列。
- 工作室及其留存业务表使用 `Restrict` 保护历史。账号、原稿通过归档下架。

数据库层要守住的 6 条硬约束：

1. 同一账号 + 同一版本只有一条任务，`UNIQUE ("accountId","variantId")`。
2. 同一账号同一时刻最多一条 `dispatching`，部分唯一索引兜底。
3. 版本快照不可变，图片只能来自同一工作室的同一原稿。
4. 任务、素材、审批、回执和事件通过触发器校验工作室。任务必须匹配同平台账号，回执截图必须来自本任务。
5. `TaskEvent` 只追加。触发器拒绝行修改和删除，应用角色只能读和追加。状态变化与事件由同一事务提交。
6. 工作室的留存业务数据使用 `Restrict`。临时授权记录和可重建的平台图片缓存按有效期清理。应用数据库角色不能删除工作室。

## 1. 设计原则

### 1.1 工作室是租户边界

每张业务表都直接或间接带 `workspaceId`。首版由服务层校验成员权限并按工作室查询，由触发器保护关联写入。API 和 Worker 的跨工作室用例均纳入回归测试。

### 1.2 版本只追加，不原地改

`Variant` 一旦插入，标题、正文、话题、图片、封面、投稿字段和 `contentHash` 都不允许 `UPDATE`。
改稿、换图、调顺序、换封面、重新生成，统统插入新 `Variant` 和新 `VariantAsset`，再把旧版置为
`superseded`。这样任务、审批、回执永远能指向一个不会变的快照。

### 1.3 任务一账号一版本一行

`PublishTask` 的 `(accountId, variantId)` 唯一。重复排期返回已有任务；调期只改 `scheduledAt`，
保留原 `id` 和原 `idempotencyKey`。失败重试也写回原行。

### 1.4 当前结果 + 历史事件

`PublishResult` 保存当前有效回执，每条任务一行。更正前的旧回执、旧链接、旧截图引用写进
`TaskEvent.details`。这样列表查询简单，历史又不会丢。

### 1.5 数据库管硬约束，应用管状态机

唯一、非空、外键、行内检查和部分索引由数据库约束。应用在事务内校验权限和业务状态，数据库触发器保护快照、事件和工作室归属。

### 1.6 归档代替物理删除

首版保留工作室，账号和原稿通过归档下架，历史版本、审批、素材、任务、回执及事件继续可读。留存表引用工作室使用 `ON DELETE RESTRICT`，间接引用通过各自的保护外键保留。迁移角色拥有数据表，API 与 Worker 使用独立的应用数据库角色，该角色没有 `Workspace` 的 `DELETE` 和 `TRUNCATE` 权限。 [PostgreSQL 权限](https://www.postgresql.org/docs/16/ddl-priv.html)

`OAuthState` 和可选 `PlatformMediaRef` 按有效期清理。首版的工作室操作涵盖创建、切换及成员和配置管理。

### 1.7 时间类型和接口边界

数据库的业务时间统一为 `timestamptz(3)`，Prisma 字段使用 `DateTime @db.Timestamptz(3)`。API 接收带偏移的 ISO 8601 时间并返回 UTC 时间，页面按用户选择的时区展示。Worker 直接比较时间列与 PostgreSQL 时钟。旧列按 §4.3.0 的迁移规则转换。 [PostgreSQL 日期时间类型](https://www.postgresql.org/docs/16/datatype-datetime.html) · [Prisma PostgreSQL 类型映射](https://www.prisma.io/docs/orm/v6/reference/prisma-schema-reference#datetime)

## 3. 关系总览

```text
User ──< Membership >── Workspace
Workspace ──< Manuscript ──< Asset
Workspace ──< ChannelAccount
Workspace ──< Variant >── Manuscript
Variant ──< VariantAsset >── Asset
Variant ── Approval (1:1)
Variant ──< VariantRejection
Variant ──< PublishTask >── ChannelAccount
PublishTask ── PublishResult (1:1)
PublishTask ──< TaskEvent
PublishTask ──< NotificationDelivery
ChannelAccount ──< OAuthState
ChannelAccount ──< PlatformMediaRef >── Asset
Workspace ── NotificationSetting (1:1)
```

读法：`A ──< B` 是一对多，`A >── B` 是多对一，`A ── B (1:1)` 是一对一。

## 4. 可执行 SQL

> 以下 SQL 用于说明约束与事务。建库以仓库迁移为准，DBX 操作见 [DBX 初始化](#dbx-初始化)。
> 外键和 `CHECK` 可先用 `NOT VALID` 建立，再用 `VALIDATE CONSTRAINT` 校验历史行。唯一索引和 `NOT NULL` 按各自的迁移步骤建立。

### 4.1 新增枚举

迁移检查当前 schema 内每个枚举的值及顺序。定义一致时复用，缺失时创建，定义不匹配时回滚。有依赖的枚举随已提交的迁移演进。 [枚举迁移](../apps/api/prisma/migrations/202611200001_database_design_v13/migration.sql)

| 枚举 | 顺序 |
|---|---|
| `AssetKind` | `manuscript_image`、`task_evidence` |
| `GenerationSource` | `import`、`rule`、`model`、`manual` |
| `TaskEventKind` | `created`、`rescheduled`、`paused`、`claimed`、`handed_off`、`result`、`verified`、`canceled`、`retried`、`corrected`、`late_receipt`、`reminder`、`note` |
| `NotificationKind` | `handoff_ready`、`overdue_reminder` |
| `NotificationStatus` | `pending`、`sending`、`sent`、`failed`、`skipped` |
| `PublishResultState` | `submitted`、`under_review`、`published`、`failed`、`unknown` |
| `AuthStatus` | `pending`、`active`、`expired`、`revoked` |

### 4.2 新增表

#### 4.2.1 工作室通知配置

```sql
CREATE TABLE "NotificationSetting" (
  "workspaceId"          text PRIMARY KEY
                           REFERENCES "Workspace"("id") ON DELETE RESTRICT,
  "provider"             text NOT NULL DEFAULT 'feishu',
  "enabled"              boolean NOT NULL DEFAULT false,
  "webhookCiphertext"    text,
  "webhookKeyId"         text,
  "signSecretCiphertext" text,
  "signSecretKeyId"      text,
  "updatedById"          text REFERENCES "User"("id") ON DELETE RESTRICT,
  "updatedAt"            timestamptz(3) NOT NULL DEFAULT now(),
  CONSTRAINT "NotificationSetting_provider_check"
    CHECK ("provider" = 'feishu'),
  CONSTRAINT "NotificationSetting_webhook_check"
    CHECK (NOT "enabled" OR "webhookCiphertext" IS NOT NULL),
  CONSTRAINT "NotificationSetting_webhook_key_check"
    CHECK (("webhookCiphertext" IS NULL) = ("webhookKeyId" IS NULL)),
  CONSTRAINT "NotificationSetting_sign_key_check"
    CHECK (("signSecretCiphertext" IS NULL) = ("signSecretKeyId" IS NULL))
);
```

要点：

- webhook 和签名密钥各自与相应 `keyId` 成对写入、轮换和清除。启用和关闭 API 只返回配置状态。
- 一个工作室一行，查询时 `LEFT JOIN`，没有配置就按“飞书关闭、站内待办照常”处理。
- 签名密钥可以没有（飞书自定义机器人签名是可选的），webhook 在启用时必须有。

#### 4.2.2 B 站授权一次性 state

```sql
CREATE TABLE "OAuthState" (
  "id"          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "workspaceId" text NOT NULL REFERENCES "Workspace"("id") ON DELETE CASCADE,
  "accountId"   text NOT NULL REFERENCES "ChannelAccount"("id") ON DELETE CASCADE,
  "userId"      text NOT NULL REFERENCES "User"("id") ON DELETE CASCADE,
  "platform"    "Platform" NOT NULL,
  "stateHash"   char(64) NOT NULL,
  "expiresAt"   timestamptz(3) NOT NULL,
  "consumedAt"  timestamptz(3),
  "createdAt"   timestamptz(3) NOT NULL DEFAULT now(),
  CONSTRAINT "OAuthState_hash_check" CHECK ("stateHash" ~ '^[0-9a-f]{64}$')
);

CREATE UNIQUE INDEX "OAuthState_stateHash_key" ON "OAuthState"("stateHash");
CREATE INDEX "OAuthState_open_idx" ON "OAuthState"("expiresAt")
  WHERE "consumedAt" IS NULL;
```

要点：

- 保存 `state` 的 SHA-256。完成会话、工作室、账号、平台及操作人校验后，用一条带条件的 `UPDATE` 消费。返回一行并提交消费后继续交换凭据，返回零行时拒绝回调。
- `expiresAt` 建议 10 分钟；过期和已消费的行由定时任务清理。
- `platform` 首版只有 `bilibili`，未来扩平台不用改表。

```sql
UPDATE "OAuthState"
SET "consumedAt" = clock_timestamp()
WHERE "stateHash" = $1
  AND "workspaceId" = $2 AND "accountId" = $3
  AND "userId" = $4 AND "platform" = $5
  AND "consumedAt" IS NULL AND "expiresAt" > clock_timestamp()
RETURNING "id", "workspaceId", "accountId", "userId", "platform";
```

#### 4.2.3 版本图片快照

```sql
CREATE TABLE "VariantAsset" (
  "variantId" text NOT NULL REFERENCES "Variant"("id") ON DELETE RESTRICT,
  "assetId"   text NOT NULL REFERENCES "Asset"("id") ON DELETE RESTRICT,
  "position"  integer NOT NULL,
  "isCover"   boolean NOT NULL DEFAULT false,
  CONSTRAINT "VariantAsset_pkey" PRIMARY KEY ("variantId", "assetId"),
  CONSTRAINT "VariantAsset_position_check" CHECK ("position" >= 0),
  CONSTRAINT "VariantAsset_unique_position" UNIQUE ("variantId", "position")
);

CREATE UNIQUE INDEX "VariantAsset_one_cover"
  ON "VariantAsset"("variantId") WHERE "isCover";
CREATE INDEX "VariantAsset_asset_idx" ON "VariantAsset"("assetId");
```

要点：

- `position` 从 0 开始，就是发布时的图片顺序。
- 一个版本最多一个封面；小红书首图即封面，B 站允许单独指定封面。
- 同一素材在同一版本里只出现一次，`PRIMARY KEY (variantId, assetId)`。
- 封面必须来自本版本快照，触发器校验图片与版本属于同一工作室、同一原稿。
- 不设 `workspaceId` 列：版本已经带工作室，图片归属由触发器保证，少一列少一处不一致。

#### 4.2.4 审核退回

```sql
CREATE TABLE "VariantRejection" (
  "id"          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "workspaceId" text NOT NULL REFERENCES "Workspace"("id") ON DELETE RESTRICT,
  "variantId"   text NOT NULL REFERENCES "Variant"("id") ON DELETE RESTRICT,
  "reviewerId"  text NOT NULL REFERENCES "User"("id") ON DELETE RESTRICT,
  "reason"      text NOT NULL,
  "createdAt"   timestamptz(3) NOT NULL DEFAULT now(),
  CONSTRAINT "VariantRejection_reason_check"
    CHECK (length(btrim("reason")) > 0)
);

CREATE INDEX "VariantRejection_variant_idx"
  ON "VariantRejection"("variantId", "createdAt" DESC);
```

要点：

- 退回只针对 `draft`；已确认的版本不能退回，只能改出新版本。
- 退回不删确认记录；同一版本可以有多条退回记录，按时间倒序展示。
- 作者待办由“最新版本是 draft 且存在 rejection”推导，不单独建待办表。

#### 4.2.5 任务事件流水

```sql
CREATE TABLE "TaskEvent" (
  "id"          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  "workspaceId" text NOT NULL REFERENCES "Workspace"("id") ON DELETE RESTRICT,
  "taskId"      text NOT NULL REFERENCES "PublishTask"("id") ON DELETE RESTRICT,
  "kind"        "TaskEventKind" NOT NULL,
  "fromStatus"  "TaskStatus",
  "toStatus"    "TaskStatus",
  "actorId"     text REFERENCES "User"("id") ON DELETE RESTRICT,
  "reason"      text,
  "leaseId"     uuid,
  "details"     jsonb NOT NULL DEFAULT '{}'::jsonb,
  "createdAt"   timestamptz(3) NOT NULL DEFAULT now(),
  CONSTRAINT "TaskEvent_correction_details_check"
    CHECK ("kind" <> 'corrected'
           OR COALESCE(jsonb_typeof("details" -> 'previous') = 'object'
                   AND jsonb_typeof("details" -> 'next') = 'object'
                   AND jsonb_typeof("details" -> 'reason') = 'string'
                   AND btrim("details" ->> 'reason') <> '', false))
);

CREATE INDEX "TaskEvent_task_id_idx" ON "TaskEvent"("taskId", "id");
CREATE INDEX "TaskEvent_workspace_created_idx"
  ON "TaskEvent"("workspaceId", "createdAt" DESC);
```

要点：

- `id` 用数据库递增，配合 `(taskId, id)` 索引保留同一任务的写入顺序；API 里序列化为字符串，避免 JS 精度问题。
- `fromStatus`/`toStatus` 记录迁移前后状态；首次排期、提醒、迟到回执可以只填一边或都不填。
- `actorId` 为空表示系统操作（Worker、定时任务）；用户操作必须填。
- `details` 只放受控字段，例如改期前后时间、更正前后的作品 ID/链接/证据、核对结论；不放平台完整响应和凭据。
- 事件只追加：触发器拒绝 `UPDATE` 和 `DELETE`。

#### 4.2.6 飞书投递记录

```sql
CREATE TABLE "NotificationDelivery" (
  "id"          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "workspaceId" text NOT NULL REFERENCES "Workspace"("id") ON DELETE RESTRICT,
  "taskId"      text NOT NULL REFERENCES "PublishTask"("id") ON DELETE RESTRICT,
  "kind"        "NotificationKind" NOT NULL,
  "dedupeKey"   text NOT NULL,
  "provider"    text NOT NULL DEFAULT 'feishu',
  "status"      "NotificationStatus" NOT NULL DEFAULT 'pending',
  "attempts"    integer NOT NULL DEFAULT 0,
  "scheduledAt" timestamptz(3) NOT NULL,
  "nextAttemptAt" timestamptz(3),
  "leaseId"     uuid,
  "leaseExpiresAt" timestamptz(3),
  "lastError"   text,
  "sentAt"      timestamptz(3),
  "createdAt"   timestamptz(3) NOT NULL DEFAULT now(),
  "updatedAt"   timestamptz(3) NOT NULL DEFAULT now(),
  CONSTRAINT "NotificationDelivery_unique"
    UNIQUE ("taskId", "kind", "dedupeKey"),
  CONSTRAINT "NotificationDelivery_attempts_check" CHECK ("attempts" BETWEEN 0 AND 4),
  CONSTRAINT "NotificationDelivery_next_attempt_check"
    CHECK (("status" = 'pending') = ("nextAttemptAt" IS NOT NULL)),
  CONSTRAINT "NotificationDelivery_lease_check"
    CHECK (("status" = 'sending') = ("leaseId" IS NOT NULL)
           AND ("leaseId" IS NULL) = ("leaseExpiresAt" IS NULL)),
  CONSTRAINT "NotificationDelivery_dedupe_check"
    CHECK (length(btrim("dedupeKey")) > 0),
  CONSTRAINT "NotificationDelivery_provider_check"
    CHECK ("provider" = 'feishu')
);

CREATE INDEX "NotificationDelivery_retry_idx"
  ON "NotificationDelivery"("nextAttemptAt", "id")
  WHERE "status" = 'pending';
```

要点：

- 同一轮交接的两类提醒各一行。用 `handoff:<handedOffAt 时间戳>` 和 `overdue:<handedOffAt 时间戳>` 去重。计划时间分别为交接时间和交接后 4 小时。
- `pending` 表示到点可领或等待重试，创建时 `nextAttemptAt = scheduledAt`。`sending` 表示已领取。飞书确认接收为 `sent`。重试耗尽、永久失败、投递结果未知为 `failed`。逾期、关闭飞书或任务已处理为 `skipped`。后三种为终态，详情显示脱敏原因。
- 投递窗口为 `scheduledAt` 起 30 分钟，最多 4 次含首次。明确未送达的临时错误在上次尝试后依次间隔 1、5、15 分钟重试，下一次必须仍在窗口内。索引筛选 `pending`，扫描查询比较 `nextAttemptAt` 与数据库时钟。领取与重启处理见 §6.6。 [飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)

#### 4.2.7 平台素材引用（可选）

```sql
CREATE TABLE "PlatformMediaRef" (
  "id"          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "workspaceId" text NOT NULL REFERENCES "Workspace"("id") ON DELETE CASCADE,
  "accountId"   text NOT NULL REFERENCES "ChannelAccount"("id") ON DELETE CASCADE,
  "assetId"     text NOT NULL REFERENCES "Asset"("id") ON DELETE RESTRICT,
  "remoteUrl"   text NOT NULL,
  "expiresAt"   timestamptz(3),
  "createdAt"   timestamptz(3) NOT NULL DEFAULT now(),
  CONSTRAINT "PlatformMediaRef_unique" UNIQUE ("accountId", "assetId")
);

CREATE INDEX "PlatformMediaRef_asset_idx" ON "PlatformMediaRef"("assetId");
```

要点：

- 首版默认随投稿上传图片。确认平台 URL 允许复用且需要减少重复上传时，按账号启用缓存。
- 平台提供有效期时写入 `expiresAt`。到期后重新上传并更新缓存行。
- 启用此表时，新增和更新缓存行都须启用 §4.5.9 的归属校验。

CREATE OR REPLACE FUNCTION "guard_variant_update"()
RETURNS trigger

BEGIN
  IF NEW."workspaceId"    IS DISTINCT FROM OLD."workspaceId"
     OR NEW."manuscriptId"   IS DISTINCT FROM OLD."manuscriptId"
     OR NEW."platform"      IS DISTINCT FROM OLD."platform"
     OR NEW."version"       IS DISTINCT FROM OLD."version"
     OR NEW."title"         IS DISTINCT FROM OLD."title"
     OR NEW."body"          IS DISTINCT FROM OLD."body"
     OR NEW."tags"          IS DISTINCT FROM OLD."tags"

     OR NEW."contentHash"   IS DISTINCT FROM OLD."contentHash"
     OR NEW."snapshotVersion" IS DISTINCT FROM OLD."snapshotVersion"
  THEN
    RAISE EXCEPTION '版本快照不可原地修改，请创建新版本' USING ERRCODE = 'MA002';
  END IF;

  IF OLD."sealedAt" IS NOT NULL AND NEW."sealedAt" IS DISTINCT FROM OLD."sealedAt" THEN
    RAISE EXCEPTION '版本封存后不可重新打开' USING ERRCODE = 'MA002';
  END IF;

  IF NEW."status" IS DISTINCT FROM OLD."status" AND NOT (
       (OLD."status" = 'draft'    AND NEW."status" IN ('approved', 'superseded'))
    OR (OLD."status" = 'approved' AND NEW."status" = 'superseded')
  ) THEN
    RAISE EXCEPTION '非法版本状态迁移: % -> %', OLD."status", NEW."status" USING ERRCODE = 'MA002';
  END IF;

  RETURN NEW;
END $$;

CREATE TRIGGER "Variant_immutable"
BEFORE UPDATE ON "Variant"
FOR EACH ROW EXECUTE FUNCTION "guard_variant_update"();

`sealedAt` 只能从空值设置一次。`status` 和 `supersededAt` 按状态机更新。改稿、换图、换封面、改投稿字段都要插入新版本。

#### 4.5.10 数据库错误契约

写入服务先校验会话、角色和工作室归属。数据库触发器以 SQLSTATE 表达写入失败原因，HTTP 按下表映射。

| SQLSTATE | 失败原因 | HTTP |
|---|---|---|
| `MA001` | 所属资源不存在、跨工作室引用，或授权绑定不可见 | `404` |
| `MA002` | 版本封存、审计只追加、实际通道已确定或其他状态冲突 | `409` |
| `MA003` | 同工作室内的原稿、任务证据、平台或回执字段不匹配 | `400` |

依赖这套映射的写操作使用 Prisma 参数化 `$queryRaw` 或 `$executeRaw`。事务回滚后从 `P2010.meta.code` 读取 SQLSTATE，用应用自己的提示文本构造响应。唯一约束冲突按各写入口的幂等或并发规则处理。未识别的异常按内部错误处理。SQLSTATE、数据库消息和触发器明细留在服务端。 [PostgreSQL RAISE](https://www.postgresql.org/docs/16/plpgsql-errors-and-messages.html) · [Prisma 错误码](https://www.prisma.io/docs/orm/v6/reference/error-reference#p2010)

### 4.6 状态机的新增转换

现有 `packages/shared/src/status.ts` 和文档有出入，数据库设计按文档为准。迁移/改代码前需要补：

| 当前 | 目标 | 场景 | 是否已有 |
|---|---|---|---|
| `handed_off` | `canceled` | 负责人核实尚未发布后取消 | 缺 |
| `failed` | `published` | 补发完成、附作品证据后更正 | 缺 |
| `canceled` | `published` | 负责人核实原任务的作品已发布，通过回填接口提供证据及原因，原任务只更正一次 | 缺 |
| `verified` | `submitted` | 待核实确认已受理，继续回读 | 缺 |

另外 `verified` 后仍可 `published` / `failed` / `scheduled`，已有。

状态机由应用层执行，数据库保留实际发生的 `fromStatus`、`toStatus` 及事件。已取消任务仅开放负责人的已发布更正，领取和重试入口均拒绝已取消任务。仍无结论的任务保持 `unknown`。

## 5. 关键口径

### 5.1 contentHash

覆盖范围必须包括发布时会变的全部内容：

```text
sha256(stableStringify({
  platform,
  title: title.trim(),
  body: body.trim(),
  tags,                       // 保持顺序
  assets: [{ assetId, position, isCover }],  // 按 position 排序
  platformFields
}))
```

注意：

- `packages/shared` 提供唯一的 `stableStringify`。序列化时递归按键的 UTF-16 编码顺序直接写出对象成员，数组按输入顺序写出。素材数组先按 `position` 排序，`tags` 保持原顺序。对无缩进的 UTF-8 JSON 计算 SHA-256。生成、确认和发布校验使用同一函数。
- `snapshotVersion=1` 使用新公式。`snapshotVersion=0` 或 `2` 的历史版本保留原有文本指纹。回归用例用嵌套对象的不同键顺序及 `jsonb` 往返验证同源快照哈希一致，并验证换图顺序会改变哈希。
- 图片换顺序、换封面、改投稿字段都改变哈希，因此必须产生新版本，而不是改旧版。
- `Variant.contentHash` 是版本快照的指纹；`Approval.snapshotHash` 必须等于它。
- `PublishTask.variantContentHash` 是排期时抄一份，保证任务证据和幂等键不依赖后续数据变化。

### 5.2 idempotencyKey

新公式（去掉时间输入）：

```text
sha256(JSON.stringify([accountId, variantId, variantContentHash]))
```

规则：

- 同一账号 + 同一版本 + 同一内容只生成一条任务，靠 `UNIQUE ("accountId","variantId")` 判定重复。
- 调期、重试沿用既有任务和幂等键。同一账号需要发布新快照时，以新 `variantId` 创建任务。
- 迁移前的老任务保留原 `idempotencyKey`，不重算；新任务用新公式。两种格式共存在同一列里，不影响唯一性。

### 5.3 租约 lease

- 领取时在事务内写 `status='dispatching'`、新的 `leaseId`、`leaseExpiresAt`、`claimedAt` 和 `attempts+1`。更新成功后同事务写 `TaskEvent('claimed')`。
- 回执必须同时匹配 `taskId`、`status='dispatching'`、`leaseId`，并且 `leaseExpiresAt > clock_timestamp()`。
- 完成或失败时清空 `leaseId`/`leaseExpiresAt`，状态离开 `dispatching`。
- 超时回收匹配任务、`dispatching` 状态和同一租约，且 `leaseExpiresAt <= clock_timestamp()` 时转为 `unknown`，同事务清理租约并记录事件，保留已知平台证据。
- 部分唯一索引 `PublishTask_one_dispatching_per_account` 保证同账号最多一条活跃派发；冲突时跳过该账号。
- 迟到回执不覆盖新状态，只追加 `late_receipt` 事件，`details` 里带旧 `leaseId` 和平台证据。

### 5.4 快照与重审

- 新版本使用 `snapshotVersion=1`。事务内先锁原稿，按选定素材的 `assetId`、`position`、`isCover` 算出 `contentHash`，插入 `Variant` 与 `VariantAsset`，设置 `sealedAt` 后整体提交。发布时只取封存版本中的素材清单。
- 迁移时按原稿图片补齐旧版本的参考快照并封存，标记 `snapshotVersion=2`。旧审批的 `snapshotHash` 保持 `NULL`，旧待发任务暂停。从旧版复制生成 `version+1`、`snapshotVersion=1` 的新版本，重新确认后再排期。
- `POST /variants/{id}/confirm` 在同一事务内核对当前版本已封存、有完整快照且 `contentHash` 可复算，再写 `Approval`。数据库检查哈希格式。排期和领取在持锁事务中核对审批、版本及任务上的哈希一致。
- 重复确认使用 `INSERT ... ON CONFLICT ("variantId") DO NOTHING RETURNING *`。无新行时查询已有审批并返回首次确认记录。

### 5.5 证据

- 原稿图：`Asset.manuscriptId` 非空，`kind='manuscript_image'`。
- 任务截图：`Asset.taskId` 非空，`kind='task_evidence'`，通过任务权限下载。回执引用的截图须与回执工作室及任务同时匹配。
- 已发布证据按 §4.3.7 校验。人工提交提供作品链接或本任务截图。官方回读确认已发表后，可以保存已核验的文章 ID 和平台发表时间。
- 更正：旧回执写 `TaskEvent.details`，新回执覆盖 `PublishResult`。
- 事件和回执都不存平台完整响应、令牌、webhook 密钥。

回执历史的具体约定（对应“保留好记录”）：

- 普通回执写一条 `TaskEvent(kind='result')`。更正写一条 `TaskEvent(kind='corrected')`，与当前回执同事务提交。
- 更正的 `details` 至少包含以下字段。

  ```json
  {
    "previous": {
      "state": "failed",
      "remoteId": null,
      "remoteUrl": null,
      "evidenceAssetId": null,
      "note": "平台返回失败"
    },
    "next": {
      "state": "published",
      "remoteId": "BV1xx",
      "remoteUrl": "https://...",
      "evidenceAssetId": "uuid"
    },
    "reason": "补发完成，附作品链接"
  }
  ```

- `TaskEvent_correction_details_check` 要求更正事件包含 `previous`、`next` 对象和非空的 `reason` 字符串。
- 已取消更正时，`previous` 同时保存原取消人、时间和原因以及旧回执。历史行缺少取消人时保留未知来源。
- 列表页只读 `PublishResult` 当前值；详情页按 `TaskEvent(kind in ('result','corrected'))` 倒序展示历史。

## 6. 并发与事务

### 6.0 服务层事务与加锁顺序

改稿、生成、审核、排期、调期、重试、归档和领取由服务层开启 `ReadCommitted` 事务，共用同一套取锁方法。Controller 校验输入并调用服务。

1. 先收集本次操作涉及的资源 ID。按 `Manuscript → Variant → ChannelAccount → PublishTask` 获取所需行锁，同表按 ID 升序，查询限定工作室。批量修改前按这个顺序锁定全部目标行。
2. 取得锁后重新校验关联关系、审批、可用性和状态。插入 `VariantAsset` 前持有所属 `Variant` 的锁，触发器复用同一行锁，创建并封存快照也在同一事务内完成。
3. 只涉及任务回执、事件和提醒的事务从 `PublishTask` 开始，随后写入对应记录。有投递行锁时已先取得所属任务锁。事务中途发现需要更早顺位的锁时，回滚并从完整资源清单重新开始。

改稿和重生成锁住原稿后再计算新版本号。原生 SQL 写入显式维护 `updatedAt`，回执更正同时刷新 `recordedAt`。领取和投递提交数据库事务后才调用外部接口。对于可安全重跑的数据库事务，遇到 `40P01`、`40001` 或 Prisma `P2034` 时从头重试，最多尝试三次。回执持久化可以单独重试，已发出的外部请求沿用原租约和核实规则。 [PostgreSQL 行锁与死锁](https://www.postgresql.org/docs/16/explicit-locking.html) · [Prisma 事务重试](https://www.prisma.io/docs/orm/prisma-client/queries/transactions)

### 6.1 领取任务

```text
BEGIN
  -- 使用 §6.0 的取锁方法，再复核工作室归属、已审快照、账号可用性和到期时间。
  -- 复核未通过，或该账号已有 dispatching 任务时，结束事务并跳过该候选。
  -- $executionChannel 取实际解析得到的适配器类型。已记录的通道与解析结果不一致时，报告任务无法派发的原因。

  UPDATE "PublishTask"
  SET "status" = 'dispatching',
      "executionChannel" = COALESCE("executionChannel", $executionChannel),
      "leaseId" = $leaseId,
      "leaseExpiresAt" = clock_timestamp() + interval '45 seconds',
      "claimedAt" = clock_timestamp(),
      "updatedAt" = clock_timestamp(),
      "attempts" = "attempts" + 1
  WHERE "id" = $taskId
    AND "workspaceId" = $workspaceId
    AND "accountId" = $accountId
    AND "status" = 'scheduled'
    AND ("executionChannel" IS NULL OR "executionChannel" = $executionChannel)
    AND "scheduledAt" <= clock_timestamp()
  RETURNING "id", "workspaceId", "leaseId", "executionChannel";

  -- 仅对 UPDATE 返回的任务写 TaskEvent(kind='claimed')，含实际通道。返回零行时结束事务。
COMMIT;
-- 仅在有领取结果且事务提交成功后进入交接或调用平台。
```

### 6.2 回写结果

```text
BEGIN
  -- 锁定当前任务并读取其状态，核对来件归属和租约。
  UPDATE "PublishTask"
  SET "status" = $newStatus,
      "leaseId" = NULL,
      "leaseExpiresAt" = NULL,
      "updatedAt" = clock_timestamp(),
      "lastError" = $error
  WHERE "id" = $taskId
    AND "workspaceId" = $workspaceId
    AND "status" = 'dispatching'
    AND "leaseId" = $leaseId
    AND "leaseExpiresAt" > clock_timestamp()
  RETURNING "id";

  -- 返回一行时，按回执类型写入结果，并追加一条对应事件。
  -- 返回零行且当前任务归属有效时，只追加 late_receipt，保留旧租约和回执证据。
COMMIT;
```

任何一步失败整体回滚。失效租约的来件不会更新当前任务或 `PublishResult`。

官方通道第一次受理时，在回写事务内保存 `submitted` 和文章 ID。状态回读以已存文章 ID 和预期任务状态为更新条件。读取失败、遇到未知平台状态或缺少作品证据时，保留已有可核对数据，继续等待核实。人工交接只写交接状态和事件，回填后再登记当前回执。

### 6.4 归档

账号归档：

```text
BEGIN
  SELECT ... FROM "ChannelAccount" WHERE "id" = $id AND "workspaceId" = $workspaceId FOR UPDATE;
  -- 统计 scheduled/dispatching/handed_off/submitted/under_review
  -- 有活跃任务返回 409
  UPDATE "ChannelAccount" SET "archivedAt" = now(), "archivedById" = $userId
  WHERE "id" = $id AND "workspaceId" = $workspaceId AND "archivedAt" IS NULL;

```

原稿归档：

```text
BEGIN
  SELECT ... FROM "Manuscript" WHERE "id" = $id AND "workspaceId" = $workspaceId FOR UPDATE;
  SELECT t."id" FROM "PublishTask" t
  JOIN "Variant" v ON v."id" = t."variantId"
  WHERE t."workspaceId" = $workspaceId AND v."manuscriptId" = $id AND t."status" = 'scheduled'
  ORDER BY t."id" FOR UPDATE OF t;
  -- $lockedTaskIds 取上面已锁定的任务 ID。
  UPDATE "Manuscript" SET "archivedAt" = now(), "archivedById" = $userId, "updatedAt" = now()
  WHERE "id" = $id AND "workspaceId" = $workspaceId AND "archivedAt" IS NULL;
  WITH paused AS (
    UPDATE "PublishTask" SET "status" = 'paused', "lastError" = '原稿已归档', "updatedAt" = now()
    WHERE "workspaceId" = $workspaceId
      AND "id" = ANY($lockedTaskIds)
      AND "status" = 'scheduled'
    RETURNING "id", "workspaceId"
  )
  INSERT INTO "TaskEvent"
    ("workspaceId", "taskId", "kind", "fromStatus", "toStatus", "actorId", "reason")
  SELECT "workspaceId", "id", 'paused', 'scheduled', 'paused', $userId, '原稿已归档'
  FROM paused;
COMMIT;
```

### 6.5 已取消任务的结果更正

复用 `POST /tasks/{id}/result` 的 `published` 分支。仅当前工作室负责人可对 `canceled` 任务使用该分支，提交非空 `reason` 和可核实的作品链接或本任务截图。截图在更正前完成资产登记。

在同一事务锁定原任务并核对角色、证据和当前状态，保留旧回执及取消字段。条件更新 `canceled → published` 并清空当前行的 `canceledAt`、`canceledById` 和 `cancelReason`。更新成功后同时保存 `PublishResult` 和唯一一条 `corrected` 事件，原取消记录及更正前数据继续可查。并发请求若发现状态已经变化，返回 `409`。原任务 ID、版本、执行通道和幂等键沿用，整个过程只更新记录。

### 6.6 飞书提醒领取与重试

1. 人工交接完成后保存站内待办。交接提醒与逾期提醒分别按 §4.2.6 的计划时间和去重键登记，逾期提醒只处理交接后 4 小时仍未回填的任务。
2. 扫描到点的 `pending` 行。先锁任务再锁投递行，复核仍为同一轮待回填交接、飞书已启用、当前时间早于 `scheduledAt + 30 分钟`。条件不符时标记 `skipped`。符合时在事务内更新为 `sending`，尝试次数加一，写入覆盖请求超时上限的租约并清空 `nextAttemptAt`。事务提交后，发送前再次核对租约、时间窗口、配置和任务状态。
3. 回写使用投递行 ID、`sending` 状态及本次未过期的 `leaseId` 作为条件。飞书确认接收时写 `sent` 和 `sentAt`。明确未接收且可重试的临时错误，在次数和窗口允许时写回 `pending` 和下一次尝试时间。超时后结果不明、永久失败或重试耗尽时写 `failed` 及原因。跳过、成功、失败或回到待重试时清除本次租约。 [飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)
4. 重启扫描过期的 `sending` 租约，条件更新为 `failed` 并记录「投递结果未知」。过期的 `pending` 行进入 `skipped`。关闭后重新开启飞书时，仅扫描当前有效的待投递提醒。所有分支都保留站内待办。

### 第 2 步：backfill（回填）

1. `Asset.kind = 'manuscript_image'`。
2. `PublishTask.variantContentHash = Variant.contentHash`。
3. `PublishResult.workspaceId = PublishTask.workspaceId`。
4. 给老 `Variant` 补 `VariantAsset` 后在同一事务封存，标记 `snapshotVersion=2`。封面为第一张，位置按素材创建时间与 ID 排序。

WITH ordered AS (
  SELECT
    v."id" AS variant_id,
    a."id" AS asset_id,
    row_number() OVER (
      PARTITION BY v."id" ORDER BY a."createdAt", a."id"
    ) AS rn
  FROM "Variant" v
  JOIN "Asset" a
    ON a."manuscriptId" = v."manuscriptId"
   AND a."kind" = 'manuscript_image'
  WHERE v."snapshotVersion" = 0
)
INSERT INTO "VariantAsset" ("variantId", "assetId", "position", "isCover")
SELECT variant_id, asset_id, rn - 1, rn = 1
FROM ordered
ON CONFLICT DO NOTHING;

UPDATE "Variant"
SET "snapshotVersion" = 2, "sealedAt" = clock_timestamp()
WHERE "snapshotVersion" = 0;

COMMIT;

  WHERE t."status" = 'scheduled'
    AND NOT EXISTS (
      SELECT 1
      FROM "Approval" ap
      JOIN "Variant" v ON v."id" = ap."variantId"

INSERT INTO "TaskEvent"

#### 旧截图与回执状态

#### 历史执行通道与操作人

- 执行通道只根据能关联到具体任务的可信回执、交接记录或部署日志回填。已知来源和依据记到任务事件。证据不足或相互冲突时保持 `NULL`。账号当前通道只用于判定新领取的可用性。
- `executionChannel` 非空表示通道已确认。为空且已有领取、交接、回执或其他派发记录时显示「历史通道未知」。尚无派发记录的任务显示「未派发」。真实发布统计纳入实际通道为 `official` 或 `manual` 的已发布任务。沙箱和历史通道未知单列。
- 按 §8.1 核对历史写入和回填人的原始 ID。找不到用户的记录保留原 ID 并标明未知来源。历史操作人外键按 §4.3.9 分表加约束和校验。

## 8. 上线前验证 SQL

### 8.1 数据体检

按迁移轮次运行适用查询。时间列检查可在旧库运行。其他查询在所需表和列已建立时运行，旧截图体检在清理 `screenshotKey` 之前执行。

```sql
-- 转换前核对时间列类型，转换后业务时间列应为 timestamp with time zone，精度为 3
SELECT table_name, column_name, data_type, datetime_precision
FROM information_schema.columns
WHERE table_schema = current_schema()
  AND table_name <> '_prisma_migrations'
  AND data_type IN ('timestamp without time zone', 'timestamp with time zone')
ORDER BY table_name, column_name;

-- 跨工作室版本图片
SELECT va.*
FROM "VariantAsset" va
JOIN "Variant" v ON v."id" = va."variantId"
JOIN "Asset" a ON a."id" = va."assetId"
WHERE v."workspaceId" <> a."workspaceId"
   OR v."manuscriptId" IS DISTINCT FROM a."manuscriptId";

-- 任务与版本、账号跨工作室，或者版本与账号的平台不同
SELECT t."id"
FROM "PublishTask" t
JOIN "Variant" v ON v."id" = t."variantId"
JOIN "ChannelAccount" a ON a."id" = t."accountId"
WHERE v."workspaceId" <> t."workspaceId"
   OR a."workspaceId" <> t."workspaceId"
   OR v."platform" <> a."platform";

-- 回执引用了其他任务或工作室的截图，或引用的素材并非任务截图
SELECT r."id"
FROM "PublishResult" r
LEFT JOIN "Asset" a ON a."id" = r."evidenceAssetId"
WHERE r."evidenceAssetId" IS NOT NULL
  AND (a."id" IS NULL
       OR a."workspaceId" IS DISTINCT FROM r."workspaceId"
       OR a."taskId" IS DISTINCT FROM r."taskId"
       OR a."kind" IS DISTINCT FROM 'task_evidence');

-- 审批与版本跨工作室
SELECT ap."id"
FROM "Approval" ap
JOIN "Variant" v ON v."id" = ap."variantId"
WHERE ap."workspaceId" <> v."workspaceId";

-- 事件/回执/投递与任务跨工作室
SELECT 'TaskEvent' AS source, e."id"::text AS id
FROM "TaskEvent" e JOIN "PublishTask" t ON t."id" = e."taskId"
WHERE e."workspaceId" <> t."workspaceId"
UNION ALL
SELECT 'PublishResult', r."id"::text
FROM "PublishResult" r JOIN "PublishTask" t ON t."id" = r."taskId"
WHERE r."workspaceId" <> t."workspaceId"
UNION ALL
SELECT 'NotificationDelivery', d."id"::text
FROM "NotificationDelivery" d JOIN "PublishTask" t ON t."id" = d."taskId"
WHERE d."workspaceId" <> t."workspaceId";

-- OAuthState 绑定关系不一致
SELECT s."id"
FROM "OAuthState" s
JOIN "ChannelAccount" a ON a."id" = s."accountId"
LEFT JOIN "Membership" m
  ON m."workspaceId" = s."workspaceId" AND m."userId" = s."userId"
WHERE a."workspaceId" <> s."workspaceId"
   OR a."platform" <> s."platform"
   OR m."id" IS NULL;

-- 同账号多条 dispatching
SELECT "accountId", count(*) AS n
FROM "PublishTask"
WHERE "status" = 'dispatching'
GROUP BY "accountId"
HAVING count(*) > 1;

-- dispatching 但缺租约（历史数据，必须先处理）
SELECT "id", "accountId", "claimedAt"
FROM "PublishTask"
WHERE "status" = 'dispatching' AND "leaseId" IS NULL;

-- 已取消但缺取消时间
SELECT "id" FROM "PublishTask"
WHERE "status" = 'canceled' AND "canceledAt" IS NULL;

-- 待发任务引用了未确认、已被取代或缺少快照的版本
SELECT t."id", t."status", v."status" AS variant_status, ap."snapshotHash"
FROM "PublishTask" t
JOIN "Variant" v ON v."id" = t."variantId"
LEFT JOIN "Approval" ap ON ap."variantId" = v."id"
WHERE t."status" = 'scheduled'
  AND (v."status" <> 'approved'
       OR v."snapshotVersion" <> 1
       OR v."sealedAt" IS NULL
       OR ap."id" IS NULL
       OR ap."snapshotHash" IS DISTINCT FROM v."contentHash");

-- 任务内容哈希与版本不一致
SELECT t."id"
FROM "PublishTask" t
JOIN "Variant" v ON v."id" = t."variantId"
WHERE t."variantContentHash" <> v."contentHash";

-- 转换枚举前核对旧回执中不属于新契约的状态
SELECT "id", "taskId", "state"
FROM "PublishResult"
WHERE "state"::text NOT IN ('submitted', 'under_review', 'published', 'failed', 'unknown');

-- 仍缺少新版证据的已发布回执
SELECT r."id", r."taskId"
FROM "PublishResult" r
WHERE r."state" = 'published'
  AND NULLIF(btrim(r."remoteUrl"), '') IS NULL
  AND r."evidenceAssetId" IS NULL
  AND (r."platformPublishedAt" IS NULL OR NULLIF(btrim(r."remoteId"), '') IS NULL);

-- 尚未建立任务素材引用的旧截图，逐条核对文件及归属
SELECT "id", "taskId"
FROM "PublishResult"
WHERE NULLIF(btrim("screenshotKey"), '') IS NOT NULL AND "evidenceAssetId" IS NULL;

-- 历史操作人无法解析的记录，保留原始 ID
WITH actors(source, id, user_id) AS (
  SELECT 'Manuscript', "id", "createdById" FROM "Manuscript"
  UNION ALL SELECT 'Variant', "id", "createdById" FROM "Variant"
  UNION ALL SELECT 'Approval', "id", "approvedById" FROM "Approval"
  UNION ALL SELECT 'PublishTask', "id", "createdById" FROM "PublishTask"
  UNION ALL SELECT 'PublishResult', "id", "recordedById" FROM "PublishResult"
)
SELECT a.source, a.id, a.user_id
FROM actors a
WHERE a.user_id IS NOT NULL AND NOT EXISTS (SELECT 1 FROM "User" u WHERE u."id" = a.user_id);

-- 存量素材的文件类型或大小不符合约束
SELECT "id", "mimeType", "size"
FROM "Asset"
WHERE "mimeType" NOT IN ('image/jpeg', 'image/png', 'image/webp')
   OR "size" <= 0 OR "size" > 20971520;

-- 重复对象 key（加唯一索引前检查）
SELECT "storageKey", count(*) AS n
FROM "Asset"
GROUP BY "storageKey"
HAVING count(*) > 1;

-- 同工作室同平台重复的平台账号 ID（加唯一索引前检查）
SELECT "workspaceId", "platform", "externalId", count(*) AS n
FROM "ChannelAccount"
WHERE "externalId" IS NOT NULL AND "archivedAt" IS NULL
GROUP BY "workspaceId", "platform", "externalId"
HAVING count(*) > 1;

-- 素材归属不一致
SELECT "id"
FROM "Asset"
WHERE ("kind" = 'manuscript_image' AND "manuscriptId" IS NULL)
   OR ("kind" = 'task_evidence' AND "taskId" IS NULL)
   OR num_nonnulls("manuscriptId", "taskId") <> 1;
```

### 8.2 约束生效后的验证

以下为 PostgreSQL 16 的空库重放、旧数据升级及业务事务验收项。已接入的迁移检查见 §7，接口与派发事务随实现验收。

| 验证 | 预期 |
|---|---|
| 从 `pg_trigger`、`pg_index`、`pg_constraint` 检查本轮应启用的对象 | 触发器已启用，部分索引谓词与设计一致，约束的验证状态匹配迁移阶段。 |
| 旧 UTC 时间列在 `Asia/Shanghai` 数据库会话中升级，再分别以 `UTC` 和 `Asia/Shanghai` 回读 | 时间瞬间及毫秒精度一致，空值保留。到期领取和租约过期在两个时区得出一致结果。 |
| 跨工作室引用、封存快照改写、同工作室的跨任务证据或跨平台排期 | PostgreSQL 分别返回 `MA001`、`MA002`、`MA003`。Prisma 写入口回滚后按 §4.5.10 映射 HTTP。 |
| 重复账号版本配对，同账号存在第二条 `dispatching` | 分别由唯一约束和部分唯一索引拒绝。 |
| 服务层在改稿、排期、归档和领取中竞争同一批记录 | 独立数据库连接共用 §6.0 顺序。事务重试后事件数量准确，已提交的外部请求无重复。 |

- 用两个并发会话消费同一 OAuth state，只有一个返回记录。已过期或绑定不匹配的请求返回零行。
- 用两个并发请求改稿和重新生成，按原稿锁串行分配版本号。确认与封存先后顺序符合 §5.4。
- 用两个领取实例竞争同账号任务，核对只有成功的更新产生 `claimed`。重复排期和重复归档核对只有实际写入产生相应事件。
- 提交过期租约与前一次租约的两类回执，核对任务和 `PublishResult` 保持原值，只有 `late_receipt` 入库。模拟事件写入失败，核对任务更新和回执一起回滚。
- 更正事件分别省略 `previous`、`next` 和 `reason`，均应被 `CHECK` 拒绝。正常更正只新增一行 `corrected`。
- 启用 `PlatformMediaRef` 时验证其账号和素材必须属于同一工作室。验证同工作室跨平台排期被拒绝。
- 检查应用角色的有效权限，`Workspace` 的 `DELETE` 和 `TRUNCATE` 及 `TaskEvent` 的 `UPDATE`、`DELETE` 和 `TRUNCATE` 均应为 `false`。使用迁移角色在临时库事务内验证有历史的工作室受外键保护。账号或原稿归档后历史证据仍可读。
- 负责人带证据更正已取消任务，核对旧取消记录和一次更正事件。编辑或运营的同类请求被拒绝，重复更正不写新事件，也没有新任务或外部投稿。
- 官方受理回执保存文章 ID，可在重启后继续回读。审核中与已发布分别入库，核对人工回填和官方回读的证据要求。迁移覆盖可回填截图、缺失截图和归属不明的旧 key。
- 在两个实例并行、关闭后重新启用以及租约过期重启的场景验证飞书。检查 4 次上限、1/5/15 分钟间隔、30 分钟窗口和终态。仍无法判断是否接收的提醒显示投递结果未知。
- 验证沙箱账号在允许沙箱的环境按配置可用。回填历史通道后，沙箱或未知记录均从真实发布统计单列。飞书密文和 `keyId` 缺任何一方的行应被约束拒绝。
