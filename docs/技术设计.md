### 服务结构

- **Web** 采用 Next.js App Router，经同源 `/api` 访问 NestJS。页面显示角色权限、当前版本、任务与异常状态。
- **API** 负责会话、工作室、稿件和素材、版本审核、任务登记及人工结果。共享 Zod 校验和状态定义供 API、Web 和 Worker 使用。
- **Worker** 独立运行，负责领取任务、生成交接待办、投递飞书、调用平台及回读结果。适配器接收已经校验的账号和内容快照，返回通道回执。
- 小红书人工通道沿用现有 `ManualHandoffAdapter`。它在本地生成回执，领取和交接可在同一个数据库事务中提交。Worker 每 5 秒使用数据库时钟扫描到期任务，并在加锁后重新校验账号和审批快照。交接包通过已审快照直接组装。
- **数据** 由托管 PostgreSQL 16 通过 Prisma 管理，文件使用私有 S3 兼容存储。对象用不可变 key 保存，下载前校验具体资源的工作室归属。B 站用官方图片上传得到平台素材引用。

### 数据和兼容

- 保留 `Workspace`、`Membership`、`ChannelAccount`、原稿、版本、审批、任务和结果的现有 ID。一个甲方一个工作室，账号可以在同一工作室继续添加。授权记录含授权方、范围、时间、有效期和凭据引用。
- 业务时间列统一为 `timestamptz(3)`，Prisma 使用 `DateTime @db.Timestamptz(3)`。切换期间停写，核对历史时间来源后转换旧列。查询和调度直接比较时刻。 [时间类型和接口边界](./数据库设计.md#17-时间类型和接口边界)
- 版本记录固化有序图片、封面、投稿参数和生成来源。内容指纹覆盖标题、正文、话题、有序素材引用、封面及投稿字段。图片换顺序、换封面或改发布字段均产生新版本。审核退回、提交回执、人工核对和结果更正留下操作者、时间、状态和原因。回填证据关联任务，与原稿素材分开保存。
- 同一账号和版本保留一条任务。新幂等键为 `[accountId, variantId, contentHash]` 序列化为 JSON 后计算的 SHA-256。以数据库 `(accountId, variantId)` 唯一约束判定重复配对。调期和重试写回原行并保留其 ID 和原幂等键，迁移也保留旧键。对历史审批缺图片快照的版本保留审批与结果记录，暂停待发旧任务，重新确认后再排期。
- 旧截图经文件与任务归属核验后回填 `evidenceAssetId`，兼容期保留经鉴权的旧读取方式。缺失或未核实的记录进入核对清单，保留原回执及旧引用。核对完成且旧读取入口退出后再清理旧列。历史操作人保留原 ID，先盘点缺失引用，再逐表收紧外键。 [历史兼容与迁移](./数据库设计.md#旧截图与回执状态)

### 审计与删除

审批和回填记录操作人，任务状态变动记录在 `TaskEvent`。账号和原稿归档后，已发布任务仍能查阅所引用的版本、素材和证据。 [数据模型](../apps/api/prisma/schema.prisma) · [账号路由](../apps/api/src/accounts/accounts.controller.ts) · [原稿路由](../apps/api/src/content/manuscripts.controller.ts)

- 新增只追加的 `TaskEvent`，包括 `id`、`taskId`、`kind`、`fromStatus`、`toStatus`、`actorId`、`reason`、`createdAt`，另有可空的 `leaseId` 和受控 `details`。初次排期的 `fromStatus` 为空，系统操作的 `actorId` 为空。锁定任务后追加事件，使用数据库递增 `id` 和 `(taskId, id)` 索引保留同一任务的写入顺序。用 `kind` 区分同状态的改期、未决核对和迟到回执。改期记录前后时间，更正记录旧回执和新证据，核对记录结论及其依据。
- 任务创建、暂停、领取、交接、回执、取消、更正、核对和重试统一经事务写入口。按预期旧状态更新任务、更新回执及追加事件，任何一步失败整体回滚。两处现有的改版入口（改稿和重新生成）共用暂停与写事件逻辑。版本审核确认保留 `Approval` 的首次确认人和时间，重复确认返回原记录。退回记录单独保存版本、处理人、时间和意见。迁移保留已有审批和回执，缺失的历史操作注明不可追溯。 [现有版本服务](../apps/api/src/content/content.service.ts) · [数据模型](../apps/api/prisma/schema.prisma)
- 账号与原稿的 `DELETE` 设置 `archivedAt`。账号有待发、派发中、已交接、已受理或审核中任务时返回 `409`。原稿归档在同一事务暂停仍待发的任务并记录审计。工作台「查看已归档」可查看和恢复资源，恢复后的待发任务仍为暂停。
- 首版保留工作室和历史业务数据。留存表对工作室以及素材、版本、任务、审批和回执之间的留存关系使用 `RESTRICT`。应用角色按数据库权限契约读写，表所有权由迁移角色持有。 [数据库权限](./数据库设计.md#438-工作室留存外键与权限)
- API 在业务事务回滚后使用数据库错误契约映射 HTTP，Worker 按同一错误码判断失败原因。 [数据库错误契约](./数据库设计.md#4510-数据库错误契约)

### 素材与凭据

- 原稿素材和任务截图共用上传校验。每张最多 20 MiB，识别并校验实际 JPEG、PNG 或 WebP，存储和下行使用服务端判定的 MIME。SVG 和其他不支持的内容返回 `415`。生成工作室前缀下的不可变 key。对象写入后登记数据库，确定登记失败时清理本次写入的对象，提交结果不明时按 key 核对登记记录后清理。新增独立素材归属时按数据库设计使用关联表。 [素材归属](./数据库设计.md#432-asset原稿图与任务截图共用)
- 素材读取同时校验工作室成员、素材行归属及对象 key 的工作室前缀。任务证据通过任务绑定读取。下行返回确定的图片 MIME 和 `X-Content-Type-Options: nosniff`。旧素材保留记录，无法确认是允许的图片时停止预览。对象目录保持私有，B 站投稿由服务端将图片上传给平台。 [上传入口](../apps/api/src/content/manuscripts.controller.ts) · [下载入口](../apps/api/src/content/assets.controller.ts) · [本地存储](../apps/api/src/content/storage.service.ts)
- 账号创建、修改和版本详情内嵌账号统一使用显式返回字段。平台令牌、飞书 webhook 与签名密钥仅在服务端加密保存和使用。飞书的两类密文各自与 `keyId` 成对写入和校验。对外返回授权或配置状态，请求日志和审计字段排除凭据与完整平台响应。当前账号列表已有脱敏，创建、更新及版本详情还需补齐。 [账号路由](../apps/api/src/accounts/accounts.controller.ts) · [版本路由](../apps/api/src/content/variants.controller.ts)

## 发布与异常处理

1. **领取。** Worker 每 2 秒检查到期任务，跨账号初始并行 3 条。候选查询按 `(scheduledAt, id)` 排序，只读候选 ID。改稿、确认、排期、归档和领取共用服务层事务及行锁入口。领取在持锁后重查到期时间、工作室、当前版本及审批、账号可用性和任务状态。 [服务层事务与加锁顺序](./数据库设计.md#60-服务层事务与加锁顺序)
2. **人工交接。** 到点提交站内待办和交接状态。交接通知及 4 小时无回填的逾期通知按任务与交接轮次去重。符合投递条件的临时失败按 1、5、15 分钟间隔重试，最多 4 次含首次，自计划时间起有效 30 分钟。已回填、已取消、关闭飞书或过期的提醒标为跳过。无法确认飞书是否接收时保留投递结果未知，站内交接照常可用。运营以作品链接或本任务截图记录已发布。 [投递事务](./数据库设计.md#66-飞书提醒领取与重试)
3. **官方投稿。** 由下方专栏契约验证 `ATC_BASE` 和 `ATC_DATA` 授权。受理、审核中及终结回执统一保存到 `PublishResult`，首次受理保存文章 ID，状态回读沿用该 ID。真实提交和回读通过后才启用官方通道。
4. **待核实。** 超时、进程中断或无文章 ID 的不明确回执进入待核实，记录原因与下一步。确认已受理就继续追踪，确认已发就登记作品。取得明确未受理证据且原审核有效时才允许重试原任务。查询失败时保留已有文章 ID 和证据。
5. **结果更正。** 确认补发完成并附作品证据后，允许 `failed → published`。负责人核实尚未发布后可将已交接任务取消。事后凭作品链接或本任务截图及更正原因，可将原任务 `canceled → published`。回执、当前任务状态和一条带原取消人、时间及原因的更正事件同事务提交。已取消任务的派发、调期和重试均拒绝。待核实确认已受理时按 `unknown → verified → submitted` 记录并继续回读。仍无法核实则保持 `unknown` 并写明下一步。

### 同账号并发与迟到回执

- 在持有 `ChannelAccount` 行锁的事务内检查当前账号没有 `dispatching` 任务，再将选中任务置为 `dispatching`，写入新的 UUID `leaseId`、`claimedAt`、尝试次数及领取事件。用 PostgreSQL 部分唯一索引约束所有领取实例。并发冲突时跳过该候选，继续扫描其他账号。提交事务后才调用通道。 [数据库索引](./数据库设计.md#44-关键索引)

- 改稿先取得原稿锁时，旧任务暂停并等待新版本重新确认。领取先完成时，已开始的提交继续绑定原来的已审版本。领取与状态回写事务都在外部请求前后各自结束。
- 回写提交结果必须匹配 `taskId`、`status = dispatching` 和本次 `leaseId`，由数据库时钟判断领取是否过期。完成时清除活跃领取凭证。超时回收用同一组条件把旧领取转为 `unknown` 并记录原因，保留已知的平台证据。过期或旧领取收到的回执只追加 `late_receipt`，供人工核对，不能覆盖较新的任务状态或回执。平台状态回读另按当前状态与已存文章 ID 条件更新，避免查询覆盖人工更正。
- 同账号串行保护的是活跃派发。领取有效期覆盖外部请求的超时上限，Worker 在发出提交前检查领取仍有效。外部是否已受理由平台证据确认，超时或重启后不得自动重新提交同一任务。
- 沙箱提交结果由稳定幂等键决定，覆盖已发布、已受理、明确失败和不确定且无文章 ID。查询根据已落库回执推进 `submitted → under_review → published`，同一输入在新实例上产生同一结果。首次领取保存实际通道，后续领取沿用该通道。历史仅按可信证据回填。界面区分未派发、历史通道未知与已确认通道。真实发布统计只计已确认的真实通道，沙箱和历史未知另列。 [历史通道回填](./数据库设计.md#历史执行通道与操作人)

### B 站专栏契约

| 环节 | 实施要求 |
|---|---|
| 授权与签名 | 应用和账号均具备相应权限。请求按官方 2.0 签名与用户 `Access-Token` 发送。图片先通过官方图片上传得到平台 URL，正文和封面引用该 URL。 [签名](https://open.bilibili.com/doc/4/8673959e-f7bb-56e6-6e68-d225f971b81b) · [投稿说明](https://open.bilibili.com/doc/4/b14b77b6-8889-8c8b-2e83-17c5a4c550fb) |
| 文章提交 | `ATC_BASE`，`POST /arcopen/fn/article/add`，`multipart/form-data`。必填 `title`、`category`、`template_id`、`summary`、`content`。标题上限 40 字，分类为官方分类列表子类 ID。按字段表校验摘要至少 200 字，正文 200–40,000 字或至少三张图片。字段表与简短示例的差异在授权联调中记录。 [官方投稿](https://open.bilibili.com/doc/4/b14b77b6-8889-8c8b-2e83-17c5a4c550fb) |
| 模板与可选字段 | `template_id` 的 `3` 用于三图，`4` 用于单图或未配封面但有头图或头部视频，`5` 用于平台默认封面。可选 `image_urls`、`tags` 用英文逗号分隔。其他可选字段为 `banner_url`、`original`、`list_id`、`up_closed_reply`、`top_video_bvid`，头图与头部视频互斥。 [官方投稿](https://open.bilibili.com/doc/4/b14b77b6-8889-8c8b-2e83-17c5a4c550fb) |
| 受理与回读 | 提交 `code = 0` 且有 `data.id` 才记受理，写 `PublishResult.state = submitted` 和文章 ID。查询用 `ATC_DATA` 的 `GET /arcopen/fn/data/art/stat`，官方示例在表单中传逗号分隔的 `ids`。取 `data[文章ID]` 的 `state`、`reason`、`publish_time`。授权账号实测样例用于固化状态映射。只有映射明确已发表且具备作品链接或平台确认的文章 ID 及发表时间时，才写 `published`。未确认时保留已有 ID 和证据。 [官方状态查询](https://open.bilibili.com/doc/4/46903ddc-1264-ddac-a3c7-559d12f32118) |

联调版本支持单封面模板 `4` 和默认模板 `5`。以同一审批快照中的 `platformFields.category`、`platformFields.summary`、有序图片和封面投稿。分类暂录官方子分类 ID。图片限制为 JPEG 或 PNG，每张至多 5 MiB。沙箱和模拟回执用于检验流程，图片返回结构、签名和完整状态枚举待获批后实测。

### 发布账号接入

工作室负责人从「发布账号」选择平台，保存开放平台核发的应用 ID 和应用密钥。应用密钥按工作室和平台加密，配置查询只返回布尔值。具备账号管理权限的负责人和编辑可以使用已保存的应用凭据连接账号。凭据保存后随下一次授权或投稿读取生效。

小红书应用需开通 Web 扫码和 `basic_info`。在账号页保存应用凭据后，点击「扫码连接小红书」，用目标账号的 App 确认并检查授权结果。核验通过的账号用于人工交接和飞书提醒。 [小红书开放平台申请入口](https://openaccount.xiaohongshu.com/console/apps) · [授权范围](https://openaccount.xiaohongshu.com/docs/scope)

保存第一份平台凭据时，服务端在 `STORAGE_LOCAL_DIR/.platform-key` 自动生成加密密钥。API 和 Worker 使用同一持久化目录，数据库和密钥文件一起备份和恢复。管理员既有的环境变量和联调命令仍可使用。工作室网页配置优先用于新连接；B 站既有环境配置账号沿用原配置，直到通过工作台重新绑定。

### B 站授权联调

1. 开放平台应用申请 `USER_INFO`、`ATC_BASE`、`ATC_DATA`，由目标账号完成授权。联调使用隔离工作室。 [身份核验](https://open.bilibili.com/doc/4/feb66f99-7d87-c206-00e7-d84164cd701c) · [授权范围查询](https://open.bilibili.com/doc/4/08f935c5-29f1-e646-85a3-0b11c2830558)
2. 负责人在「发布账号 → B 站」填写应用 ID 和密钥。通过官方流程取得账号访问令牌和有效期后，打开「连接 B 站账号」填写这两项。授权令牌到期时，取得新授权并再次绑定。目前浏览器授权回调仍待实现。
3. 启动 API、Worker 和工作台。在 B 站版本中填写子分类 ID 与摘要，审核后选用标为「专栏自动投稿」的账号排期。验收记录平台受理的文章 ID、回读状态和发表时间。待核实任务先到平台侧核对，Worker 不会自动重投。

部署环境已配好旧版 B 站环境变量时，也可继续通过命令行联调。授权截止时间使用带时区的 ISO 8601 时间。 [环境变量示例](../.env.example)

```powershell
pnpm.cmd --filter '@matrixark/api...' build
$biliToken = Read-Host 'B 站开放平台访问令牌' -AsSecureString
[System.Net.NetworkCredential]::new('', $biliToken).Password |
  pnpm.cmd --filter @matrixark/api bind:bilibili '工作室ID' '操作者用户ID' '授权截止时间'
Remove-Variable biliToken
```

### 飞书提醒联调

1. 在目标飞书群添加自定义机器人。由工作室负责人打开左侧「飞书提醒」，粘贴群机器人地址，按机器人安全设置填写签名密钥。 [飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)
2. 保存后点击「发一条测试消息」，在群里确认收到了消息。需要自动接收任务提醒时，勾选「给本工作室发送任务提醒」并保存。
3. 用已核验的小红书账号排期一条已审稿。到点查看「发布任务 → 待回填」，核对群内提醒和任务详情的投递记录。

部署时让 API 和 Worker 共用持久化存储。默认首次保存机器人时生成 `STORAGE_LOCAL_DIR/.notification-key`，备份与恢复须包含此文件。已有通过 `NOTIFICATION_CREDENTIALS_KEY` 加密的凭据继续使用原环境密钥。

### 视频素材与审核

- 原稿上传一份 MP4 和图片封面。API 流式保存视频并记录 SHA-256，单文件上限 100 MiB。视频以素材 ID 进入版本指纹，已有图文快照保留原指纹。数据库约束视频必须归属同一工作室和原稿，版本的视频引用不可改写。
- 替换视频时以同一事务创建各平台的待审版本、取代旧版本并暂停未领取的旧任务。重复上传相同文件沿用原视频。已交接、已提交及已回填任务继续指向原版本，历史视频保留。
- 工作台可预览当前视频与审核版本。人工交接包可下载审核时的视频和封面。首轮通过人工交接和沙箱开展视频排期验证。B 站视频官方适配器和账号默认值按后续阶段开发。 [接口设计](./功能与接口设计.md)

## 配置与部署

- **环境配置。** 本地使用 Node.js 24、pnpm 和 PostgreSQL。API 读取 `DATABASE_URL` 连接数据库，默认监听 `127.0.0.1:4000`。`PUBLIC_BASE_URL` 决定会话 cookie 的 `Secure` 属性。B 站官方通道默认关闭，启用需配置应用凭据和账号令牌加密密钥。飞书 webhook 和签名密钥通过工作室配置接口设置。 [配置读取](../apps/api/src/config.ts) · [环境变量示例](../.env.example)
- **启动保护。** 沙箱默认关闭。无效的布尔值、数据库地址或存储驱动在启动时报告配置错误。生产要求关闭沙箱并使用 HTTPS 的 `PUBLIC_BASE_URL`。本地登录及调试使用开发环境。数据库连接由 Prisma 随应用生命周期建立和释放，`GET /api/health` 实际查询工作室表。 [数据库连接](../apps/api/src/prisma/prisma.service.ts) · [健康接口](../apps/api/src/health.controller.ts)
- **最终打包。** Dockerfile 使用锁文件安装依赖、生成 Prisma Client、编译 API 和所需工作区包。镜像启动命令只运行 API。部署时 Compose 使用同一镜像运行一次性 `migrate` 服务，迁移成功后才启动 API。部署配置分别提供应用与迁移角色的连接地址，数据库保持独立部署。 [API Dockerfile](../infra/api.Dockerfile) · [Compose 配置](../docker-compose.yml) · [Compose 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)
- **恢复。** 托管数据库经 TLS 连接，时间点恢复至少保留 7 天，私有对象存储的历史版本覆盖该窗口。应用机恢复目标为 2 小时，数据库回档的数据损失窗口目标为 1 小时。回档后先保持派发关闭，核对稿件、素材、密钥配置和可能已提交的任务，再恢复安全的排期。 [数据库恢复示例](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html) · [对象版本恢复示例](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RestoringPreviousVersions.html)

## 本地启动与流水线

从仓库根目录安装锁定依赖。将 `.env.example` 复制为 `.env`，填写具备 `matrixark_app` 权限的登录账号。已有 DBX 本地库的地址是 `127.0.0.1:5432`，库名 `postgres`，schema 为 `public`。配置完成后启动 API，并访问 `http://127.0.0.1:4000/api/health` 验证连接。

```powershell
pnpm install --frozen-lockfile
pnpm dev:api
```

等 `pnpm dev:api` 完成编译并启动，再另开一个终端，在仓库根目录运行 `pnpm dev:worker`。Worker 使用已编译的入口，与 API 共用同一份 `.env` 和 PostgreSQL 库。

另开终端运行 `pnpm dev:web`，打开 `http://127.0.0.1:3000`。浏览器使用同源 `/api`；Next.js 默认把请求转发到 `http://127.0.0.1:4000`。API 改用其他端口时，在 Web 进程设置 `MATRIXARK_API_ORIGIN`。

GitHub Actions 在推送和 PR 时按改动路径选择检查，只改文档时跳过 API 和数据库检查。在 **Run workflow** 中可独立勾选以下任务并组合执行。 [流水线配置](../.github/workflows/matrixark.yml)

| 任务 | 检查内容 | 自动执行条件 |
|---|---|---|
| API 构建与测试 | Prisma Client 生成、工作区构建、类型检查和现有测试。 | API、共享代码或相关构建配置发生变化。 |
| PostgreSQL 16 迁移 | 原生临时 PostgreSQL 16，验证空库部署、带历史数据和已有枚举的旧库升级、重复部署及核心约束。 | 数据库结构、迁移或相关依赖发生变化。 |
| 最终 Docker 打包 | 构建 API 镜像并导出 `matrixark-api.tar.gz`。 | 在 **Run workflow** 中显式勾选。 |

新建或升级业务库时，将迁移角色的 `DATABASE_URL` 注入 `pnpm db:deploy`。首次部署先执行数据库设计中的应用权限脚本，随后用应用登录账号启动 API。 [数据库权限与迁移](./数据库设计.md#dbx-初始化)

## 工程验收

- **集成环境。** 数据库任务启动原生 PostgreSQL 16 临时实例，在 `127.0.0.1:55432` 上创建两个测试库并注入连接配置。API 的构建和现有单测在独立任务运行。后续接口集成测试使用同类隔离数据库和文件目录。 [迁移文件和 CI](./数据库设计.md#迁移文件和-ci)
- **回归用例。** 覆盖跨工作室访问、凭据脱敏、拒收伪装类型、上传失败清理、归档后审批和结果可读、审计写失败整体回滚、换图须重审、重复排期和调期。用两个独立数据库连接同时领取同一账号的不同版本任务，验证仅一个领取成功且其他账号可继续。覆盖改稿先取得锁、领取先完成、旧领取回执、沙箱重启、飞书失败、平台受理后断线和回档恢复。用 50 个账号测批量排期及结果，另测第 51 个账号可新增、查找和排期。空闲且依赖正常时，到期后 30 秒内开始交接或提交。批量场景另记排队延迟。
- **留存和异常验证。** 用实际 Prisma 基线演练 PostgreSQL 16 升级，验证应用角色不能删除工作室、旧截图兼容读、负责人更正已取消任务、历史通道统计、B 站受理后重启回读，以及飞书关闭后重开和重启都跳过已过期的提醒。 [数据库验收用例](./数据库设计.md#82-约束生效后的验证)
- **启用。** 研发直接启动，小红书人工闭环先验收。官方通道经真实账号授权投稿和状态回读后启用。沙箱结果在页面和报表显式标注。发布验收要求零重复投稿和全部待核实任务可追溯。工程演练及真实通道结果以实际记录为准。 [阶段安排](./阶段安排_v1.md) · [试用记录](./试用记录.md)
