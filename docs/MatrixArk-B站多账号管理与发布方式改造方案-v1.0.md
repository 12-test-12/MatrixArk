# MatrixArk B站多账号管理与发布方式改造方案

**版本：** v1.0\
**项目：**
[12-test-12/MatrixArk](https://github.com/12-test-12/MatrixArk)\
**范围：** 仅改造 B站，暂不涉及小红书及其他平台。

## 1. 总体目标

MatrixArk 支持个人创作者管理多个 B站账号，并在发布作品时选择三种方式：

  ---------------------------------------------------------------------------------------------------------------------------
  优先级            发布方式          标识               说明
  ----------------- ----------------- ------------------ --------------------------------------------------------------------
  1                 官方 API          `official_api`     使用 B站开放平台 OAuth 和实际获批的投稿权限，优先推荐。

  2                 本地浏览器辅助    `local_browser`    使用用户本机独立浏览器会话准备投稿；实际提交能力必须符合平台规则。

  3                 人工交接          `manual_handoff`   准备稿件、素材和文案，由用户完成发布并回填结果。
  ---------------------------------------------------------------------------------------------------------------------------

注意：现有官方 Adapter 主要涉及
B站专栏，不能把尚未实现或未获授权的视频投稿能力显示为可用。本地扫码登录也不代表平台允许无人值守自动投稿；验证码、安全验证和需要用户确认的操作由用户完成，不实现风控或验证码绕过。

### 核心原则

1.  同一个经过核验的 B站 UID，在同一工作室内应只有一个主要账号档案。
2.  同一账号可以同时拥有 OAuth 授权和本地浏览器会话。
3.  账号身份、接入方式、发布能力分开建模。
4.  每个账号使用独立 Browser Profile。
5.  Profile 长期保存，浏览器按需启动，不要求所有账号常驻。
6.  同一账号同一时间只能执行一个浏览器任务。
7.  发布任务记录用户选择的模式，并在执行前重新校验。
8.  结果未知时不能自动切换通道再次投稿。
9.  保留现有专栏 OAuth、人工交接、历史任务和回执。
10. 敏感凭据必须加密或留在用户本机受控目录。

## 2. 目标架构

### 2.1 账号主体与授权关系

建议保留现有 `ChannelAccount` 作为账号主体，并增加独立的身份和授权记录：

``` text
ChannelAccount
  ├── PlatformIdentity  # B站 UID、OAuth openid、验证来源
  ├── OAuthGrant        # 加密 Token、Scope、有效期、授权状态
  └── BrowserSession    # deviceId、profileId、verifiedUid、会话状态
```

以上为建议模型，不代表仓库中已经存在。实施前必须审计现有 Prisma Schema
和迁移历史。

### 2.2 本地 Profile

``` text
MatrixArk/
  local-data/
    browser-profiles/
      workspace-uuid/
        account-uuid-1/
        account-uuid-2/
        account-uuid-3/
```

要求： - Profile 路径由本地执行器根据内部 UUID
解析，不接受前端任意路径。 - 不同账号不共享 Cookie、LocalStorage 或
Profile 目录。 - 同一 Profile 同一时间只能被一个浏览器进程占用。 -
浏览器关闭后保留 Profile，以便恢复会话。 - 删除 BrowserSession 不应误删
OAuth 授权和历史任务。 - Profile 和 Cookie 不上传服务器。

### 2.3 发布任务路由

``` text
创建发布任务
   ↓
账号与稿件能力预检
   ↓
用户选择发布方式
   ↓
幂等检查与任务调度
   ├── official_api
   ├── local_browser
   └── manual_handoff
   ↓
统一任务状态与发布回执
```

不能只依赖 `ChannelKind` 判断执行方式。必须结合内容类型、Scope、Adapter
实现、浏览器会话和设备状态判断。

# 5. 模块 1：账号身份与授权体系重构

**优先级：P0。**

建议的数据模型：

-   `PlatformIdentity`：`accountId`、`platform`、`identityType`、`identityValue`、`verified`、`verifiedAt`、`verificationSource`。
-   `OAuthGrant`：`accountId`、`clientId`、加密
    Token、`scopes`、`expiresAt`、`status`。
-   `BrowserSession`：`accountId`、`deviceId`、`profileId`、`status`、`verifiedUid`、`lastCheckedAt`。

### 模块 1 提示词

``` text
请重构 MatrixArk 的 B站账号数据结构，将账号主体、平台身份、OAuth 授权和本地浏览器会话分离。

保留现有 ChannelAccount 作为账号主体。

设计 PlatformIdentity，保存经核验的 B站 UID 和 OAuth openid。不能将 openid 直接当作 UID，也不能通过昵称相同判断同一账号。

设计 OAuthGrant，独立保存加密后的 Access Token、Refresh Token、Scope、有效期和授权状态。

设计 BrowserSession，保存 accountId、deviceId、profileId、status、verifiedUid 和最近核验时间。实际 Profile 路径由本地执行器解析，数据库不能暴露任意文件路径。

要求：
1. 一个账号可同时拥有 OAuth 和 BrowserSession。
2. 删除浏览器会话不删除 OAuth。
3. OAuth 过期不导致浏览器会话失效。
4. 重新扫码不覆盖 OAuth。
5. 同一工作室内经核验的 UID 不得重复创建账号主体。
6. 身份无法可靠映射时不自动合并。

先审计现有 ChannelAccount、externalId、cookieCiphertext 和历史任务，再制定迁移方案。使用数据库迁移，不清空原数据。输出 Prisma Migration、类型定义和测试。
```

**验收：** 一个账号能同时存在 OAuth 和
BrowserSession，互不覆盖；历史数据完整保留。

# 7. 模块 3：官方 OAuth 改造

**优先级：P1。**

建议将 OAuth 流程调整为：

``` text
OAuth 发起
  ↓
回调与 state 校验
  ↓
获取平台身份
  ↓
加密暂存授权凭据
  ↓
检查是否已有账号
  ↓
用户确认关联或创建
  ↓
保存 OAuthGrant
```

### 模块 3 提示词

``` text
请改造 MatrixArk 当前 B站 OAuth 授权流程。

重点检查：
- apps/api/src/accounts/bilibili-oauth.ts
- apps/api/src/accounts/bilibili-account.ts
- apps/api/src/accounts/account-onboarding.service.ts

OAuth 成功后不要无条件创建 ChannelAccount。

改为：
1. 发起 OAuth。
2. 接收回调并校验 state。
3. 获取平台身份。
4. 加密暂存授权凭据。
5. 检查当前工作室是否已有账号。
6. 返回匹配结果。
7. 用户确认关联或创建。

不能使用昵称判断重复，不能直接比较 openid 与网页登录 UID。没有可靠映射时要求进一步验证。

保留现有 ATC_BASE、ATC_DATA 等权限校验逻辑，但将权限判断落实到具体能力：专栏投稿、专栏数据读取、视频投稿。尚未实现的视频能力不能显示为可用。

安全要求：
- Token 加密。
- 暂存授权有过期时间。
- state 一次性使用。
- 授权结果绑定发起授权的用户和工作室。
- Secret 不返回前端。
- 不覆盖 BrowserSession。

保留现有 B站专栏 Adapter，提供授权流程和历史账号回归测试。
```

**验收：** 已有浏览器账号可以追加 OAuth；授权不覆盖本地会话；能力按真实

# 8. 模块 4：本地浏览器管理器与多账号 Profile

**优先级：P0，个人用户多账号管理的关键。**

建议使用 Node.js + Playwright 的持久化浏览器上下文，例如
`launchPersistentContext()`。实施前确认当前 Playwright 版本和运行环境。

第一版建议全局浏览器并发数为 1，Profile 长期保存、浏览器按需启动。

### 模块 4 提示词

``` text
请为 MatrixArk 开发 B站本地浏览器管理器。

本阶段只实现账号登录、Profile 管理和身份核验，不实现自动投稿。

技术：
优先使用 Node.js + Playwright，使用 launchPersistentContext 创建独立浏览器用户配置。

多账号隔离：
1. 每个 ChannelAccount 对应独立 Browser Profile。
2. 不同账号不能共享 Cookie、LocalStorage 或 Profile 目录。
3. 同一 Profile 同一时间只能被一个浏览器进程占用。
4. 支持关闭后恢复、重新扫码、删除单个账号会话。
5. 浏览器全局并发数第一版设为 1。
6. 不要求所有账号浏览器常驻。

接入流程：
1. 创建 Profile。
2. 打开可见浏览器。
3. 导航到 B站官方登录页面。
4. 用户自行扫码和完成安全验证。
5. 等待登录完成。
6. 获取并核验 UID。
7. 将 Profile 与账号档案关联。

安全：
- Profile 不能通过前端直接访问。
- 不接受任意路径输入，使用内部 UUID。
- Cookie 和 storageState 不上传服务器。
- 使用账号级锁。
- 浏览器异常退出后释放锁。
- 不实现验证码、指纹或风控绕过。

兼容：
检查现有二维码登录和 cookieCiphertext 逻辑，不直接删除旧功能，给出迁移方案。

测试三个不同 B站账号：依次登录、关闭，再分别恢复，确认身份没有串号。
```

**验收：**
同一台电脑可保存多个独立账号登录环境；浏览器按需启动；会话恢复不串号。

# 9. 模块 5：重复账号检测与账号关联

**优先级：P0。**

  情况                       处理
  -------------------------- ------------------------------------
  相同且已核验 UID           关联已有账号
  相同 openid                检查已有 OAuth 身份映射
  昵称相同、UID 不同         不合并
  已归档账号                 提示恢复
  同一账号正在接入           阻止并发创建
  UID 与 openid 无可靠映射   不自动合并
  已有 BrowserSession        更新或重新核验，不创建重复 Profile

### 模块 5 提示词

``` text
请为 MatrixArk 开发 B站账号重复检测和账号关联服务。

目标：
同一工作室内，一个真实 B站 UID 只能有一个主要账号档案，但该账号可以同时拥有 OAuth、浏览器登录和人工交接能力。

检测规则：
1. 相同且已核验 UID：关联已有账号。
2. 相同 openid：检查已有 OAuth 身份映射。
3. 昵称相同但 UID 不同：不合并。
4. 已归档账号：提示恢复。
5. 正在接入的账号：阻止并发重复创建。
6. 无法确认 UID 与 openid 关系：不自动合并。

关联操作：
- 将 BrowserSession 关联到已有账号。
- 将 OAuthGrant 关联到已有账号。
- 更新过期会话。
- 取消绑定。
- 恢复归档账号。

事务安全：
- 检测和创建必须考虑并发。
- 使用数据库唯一约束。
- 使用事务完成身份关联。
- 不能只依赖前端查询结果。
- 保留历史任务和作品记录。

检查 PublishTask 当前 accountId + variantId 唯一约束。如果同一真实 B站 UID 被不同记录表示，设计可靠的账号主体关联或统一去重机制，不能简单删除旧账号。

测试相同 UID、相同昵称不同 UID、OAuth 与浏览器同时接入、并发添加、归档恢复和历史任务保留。
```

**验收：**
同一真实账号不会因接入方式不同重复创建；并发情况下仍能保证唯一性。

``` text
- 同一账号不能并发执行两个投稿任务。
- 浏览器准备阶段不能无限占用 Worker 租约。
- 等待用户确认时释放执行资源。
- 保留任务历史和发布回执。

验收：分别完成官方专栏、本地浏览器辅助、人工交接三种流程，互不干扰。
```

**验收：** 用户可选择真实可执行的方式；Worker
正确路由；未知结果不会重复投稿。

# 13. 模块 9：安全、迁移与完整验收

**优先级：最终验收。**

### 检查清单

-   Cookie 是否可能进入日志。
-   OAuth Secret 是否返回前端。
-   Profile 是否可能被其他工作室访问。
-   不同账号是否可能共享会话。
-   设备解绑后的本地会话如何处理。
-   删除账号是否误删历史任务。
-   浏览器异常退出是否释放锁。
-   任务锁是否存在竞态。
-   是否存在跨工作室访问。
-   OAuth 回调是否有 CSRF 防护。

必须保留现有 OAuth 账号、二维码登录账号、人工交接账号、历史任务和回执。

### 模块 9 提示词

``` text
请对 MatrixArk 的 B站多账号管理和多发布方式进行完整安全审计与回归测试。

一、安全测试
1. 检查 Cookie 是否可能出现在日志。
2. 检查 OAuth Secret 是否返回前端。
3. 检查 Browser Profile 是否可能被其他工作室访问。
4. 检查不同账号是否可能共享会话。
5. 检查设备解绑后的本地会话处理。
6. 检查删除账号时是否误删历史任务。
7. 检查浏览器异常退出后的资源释放。
8. 检查任务锁是否存在竞态。
9. 检查跨工作室账号访问。
10. 检查授权回调 CSRF 风险。

二、数据迁移
保证现有 B站官方 OAuth 账号、二维码登录账号、人工交接账号、历史发布任务和历史回执都能正常读取。
不允许清空数据库或重建用户数据。

三、功能回归
测试：
- 一个账号同时拥有 OAuth 和 BrowserSession。
- 三个不同 UID 的账号分别登录。
- 同一 UID 重复添加。
- 不同 UID 使用相同昵称。
- OAuth 过期但浏览器会话有效。
- 浏览器会话过期但 OAuth 有效。
- 设备离线。
- 浏览器崩溃。
- 任务提交结果未知。
- 人工交接。

四、性能
测试一台电脑管理 5～10 个账号；浏览器不常驻；按需启动；全局并发数为 1。观察内存、CPU 和恢复时间。

五、交付
提供测试报告、数据库迁移文件、环境变量说明、安装说明、故障排查说明、回滚方案和未完成能力清单。

不得将模拟成功作为真实发布成功。
```

**验收：**
老账号不丢失、新账号不串号、任务不重复提交、敏感信息不泄露、未实现能力如实展示。

# 15. 最终里程碑与执行顺序

## 里程碑一：多账号管理基础

完成模块 0～5。

**完成标志：**

-   同一台电脑可以管理多个个人 B站账号。
-   每个账号身份明确、登录环境隔离。
-   同一个 UID 不会因不同接入方式产生重复账号。
-   现有 OAuth 专栏能力继续可用。
-   用户可以追加或移除独立授权方式。

## 里程碑二：发布执行体系

完成模块 6～7。

**完成标志：**

-   用户可选择官方 API、本地浏览器辅助或人工交接。
-   系统根据内容类型、授权、设备和账号状态判断真实可用方式。
-   Worker 正确分发任务。
-   任务幂等和结果核实机制有效。

## 里程碑三：产品化与稳定性

完成模块 8～9。

**完成标志：**

-   账号管理体验完整。
-   异常状态可诊断。
-   敏感会话受到保护。
-   旧数据和旧功能不受破坏。

## 当前最建议立即执行

不要一次性把九个模块交给 Codex。

先将「共用开发约束」和「模块 0」一起交给
Codex，让它完成真实源码审计。审计确认后，再按模块 1、2、3 的顺序实施。

**最重要的原则：先理顺账号主体、身份映射和授权方式，再做多账号浏览器，最后接入视频投稿执行。**

账号管理与视频投稿应当分成两个里程碑。第一阶段不需要等视频投稿完成，就可以交付一个可用的
B站多账号管理基础。
