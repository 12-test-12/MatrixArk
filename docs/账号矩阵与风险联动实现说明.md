本文记录 MatrixArk 在“多账号集中管理、不依赖官方开放平台前置审批”方向上的完整改造与实现细节，作为后续开发、排障、迁移和运维的长期备忘录。全部改动保持工作室多租户隔离、加密 AAD 绑定及人工交接/官方通道兼容性。

---

## 1. 背景与解决的问题

1. **脱离官方开放平台卡点**：在开放平台应用尚未审核通过前，仍可通过 **网页扫码（QR）**、**账号密码托管**、**Cookie 导入** 三种方式接入 B 站 / 小红书账号，且接入后即可进入人工交接排期流程（`availableForHandoff: true`）；同时保留旧版仅填 UID 的 B 站 `manual_uid`（`manual-bili-uid:`）拦截策略，确保向后兼容。
2. **单一归属矩阵组**：支持跨平台创建运营矩阵组，数据模型上强制 **一个账号最多只能归属一个矩阵组**，彻底避免同一账号同时挂在多个分组下引起运营与排期混淆。
3. **风险感知与飞书联动**：建立自动体检、发布异常联动与人工上报风险闭环，通过工作台飞书群机器人实现实时告警与解除同步。

### 3.1 凭据加密与 Cookie 解析

- 实现位置：[apps/api/src/accounts/account-secrets.ts](file:///D:/MatrixArk/apps/api/src/accounts/account-secrets.ts)
- **加密**：复用 [platform-app.ts](file:///D:/MatrixArk/apps/api/src/accounts/platform-app.ts) 的 `encryptPlatformSecret` / `decryptPlatformSecret`（AES-256-GCM，`keyId = 'platform-local-v1'`），通过 AAD `['account-password' | 'account-cookie', workspaceId, accountId]` 与工作室及账号强绑定。

- **Cookie 兼容解析**：`parseCookieHeader` 同时支持标准 `Header` 字符串（允许带 `Cookie:` 前缀或换行分隔）及浏览器导出的 JSON 数组 / 键值对象，且 `validatePlatformCookie` 按平台校验必备会话键（B 站要求 `SESSDATA`，导入后再调 `nav` 接口核验登录态与 UID；小红书要求 `web_session` / `a1` / `customer-sso-sid` 等）。

### 3.2 三种账号接入方式与可控解密

- 实现位置：[apps/api/src/accounts/account-onboarding.service.ts](file:///D:/MatrixArk/apps/api/src/accounts/account-onboarding.service.ts)、[apps/api/src/accounts/accounts.controller.ts](file:///D:/MatrixArk/apps/api/src/accounts/accounts.controller.ts)
- **1）扫码接入（QR）**：
  - **B 站网页端扫码**：`POST /api/workspaces/:workspaceId/accounts/bilibili/qr` 生成 180 秒有效二维码门票（对接 `https://passport.bilibili.com/x/passport-login/web/qrcode/generate`）；`POST .../bilibili/qr/:id/poll`（带 1500ms 轮询保护）确认登录后通过 `https://api.bilibili.com/x/web-interface/nav` 核验 `mid` 与 `uname`，加密保存完整登录 Cookie（`accessMethod: 'qr_login'`，`externalId` 为 `bili-web-uid:<mid>`），并自动解除该账号此前未解决的风险事件。
  - **小红书扫码**：沿用 [xiaohongshu-identity.service.ts](file:///D:/MatrixArk/apps/api/src/accounts/xiaohongshu-identity.service.ts) 身份核验流，创建/更新时标注 `accessMethod: 'qr_login'`。
- **2）账号密码托管（Password）**：
  - `POST /api/workspaces/:workspaceId/accounts/password`：接收平台、显示名、登录账号、密码及可选 B 站 UID/主页、矩阵组、别名、标签；完整账号与密码加密存储在 `passwordCiphertext` 中，数据库明文字段仅存掩码后的 `loginIdentifier`。
- **3）Cookie 导入（Cookie）**：
  - `POST /api/workspaces/:workspaceId/accounts/cookie`：支持新增账号或针对已有账号刷新 Cookie。B 站会现场联网校验 `nav` 接口返回真实登录态，小红书按会话标识哈希生成或匹配 `xhs-cookie:<hash>` 并加密入库。
- **凭据只写不读**：
  - `GET /api/workspaces/:workspaceId/accounts/:id/credentials` 已下线；服务端不再向前端回传解密后的账号/密码或 Cookie，凭据仅用于服务端发布与体检。
- **人工交接放行判定**：
  - [publish-account.ts](file:///D:/MatrixArk/apps/api/src/accounts/publish-account.ts) 中 `isUnverifiedBilibiliAccount` 仅认定 `accessMethod === 'manual_uid'` 或 `externalId` 以 `manual-bili-uid:` 开头的历史仅 UID 记录为未核验；`qr_login`、`password`、`cookie` 均返回 `availableForHandoff: true`。

### B 站身份一致性规则（2026-11-28）

- `externalId = bili-web-uid:<UID>` 表示网页登录身份；扫码和 Cookie 导入必须通过 B 站 `nav` 接口取得真实 UID。`manual-bili-uid:<UID>` 仅表示人工登记，`pwd-<accountId>` 表示尚未绑定 UID 的密码档案；保存密码不代表已核验身份。
- OAuth 账号的 `externalId` 是开放平台返回的 openid，即使全为数字也不作为 UID。当前不根据昵称或用户指定账号 ID 自动合并 OAuth 与网页登录档案。
- 针对已有账号导入 Cookie 时，核验出的 UID 必须与已登记 UID 一致，填写的主页 UID 也必须一致。相同 UID 更新原档案并保留任务关联，主页保存为该 UID 的标准空间链接。
- 未绑定 UID 的密码档案仅在没有任何历史任务、且目标 UID 未被其他档案占用时允许首次绑定。已有历史任务的占位档案保留，用户应单独接入核验后的账号，避免历史任务被解释为另一身份的任务。
- 显式指定不存在、其他工作室或其他平台的账号 ID 返回 `404`；归档、官方、沙箱账号以及无法识别的历史身份不直接改绑网页登录态。UID 冲突返回 `409`，不覆盖原凭据。
- 首次绑定在工作室锁和账号行锁内检查；账号资料修改也先获取账号行锁，与排期共用同一锁定资源。本次无数据库结构变更，不迁移或删除历史数据。

回归用例位于 [bilibili-qr.test.mjs](../apps/api/test/bilibili-qr.test.mjs)，通过模拟平台响应和内存数据验证 UID 替换被拒绝、同 UID 续期、首次绑定、历史任务保留、重复档案及工作室隔离；该套件已加入 API CI。真实平台联调与 PostgreSQL 并发验证另行执行。

### B 站本地浏览器会话（2026-11-28）

入口为「添加账号 → 本地浏览器」和人工交接账号详情中的「授权与接入 → 独立浏览器会话」。用户打开浏览器后自行扫码、完成安全验证，再点击「检查登录」核验真实 UID；已有 UID 必须一致，新账号核验成功后加入原有账号列表。分组可在接入后通过账号列表调整。

- 使用 `playwright-core` 的持久化上下文，默认使用已安装的 Edge，可通过 `LOCAL_BROWSER_CHANNEL=chrome` 改用 Chrome。不下载或复用用户日常浏览器的 Profile。
- 默认目录为 `local-data/browser-profiles/<工作室标识哈希>/<会话 UUID>/`，其中 `profile/` 保存浏览器数据，`session.json` 保存账号关联、预期 UID、最近核验结果和时间。记录仅在当前电脑有效，尚未引入跨设备会话数据库表，因此本阶段无数据库迁移。
- 开发环境且 API 监听回环地址时默认启用；其他部署默认关闭。用 `LOCAL_BROWSER_ENABLED=true` 显式开启，`LOCAL_BROWSER_DATA_DIR` 可由部署者指定本地保存根目录。浏览器运行在 API 所在电脑，云端或无桌面容器不能直接打开用户电脑的浏览器。
- 同一数据根目录通过进程内操作互斥及跨进程文件锁限制为一个打开的浏览器。关闭窗口或正常退出 API 后释放锁，Profile 保留；重启后可从会话列表恢复。确认原 API 进程已退出后可自动清理旧进程锁；锁文件损坏时拒绝自动接管，需先确认相关浏览器均已关闭再排查本地目录。
- 第一版使用单台电脑上的单个 API 进程管理会话；文件锁用于阻止其他进程重复启动，不提供跨进程会话调度或负载均衡。
- Profile 路径只从工作室和内部会话 UUID 推导，不接收客户端路径，并拒绝目录联接或符号链接越界。Cookie 不通过接口返回，不从本地浏览器导入数据库；原有服务端加密 Cookie 保留。`local-data/` 已从 Git 和 Docker 构建上下文排除。
- 关闭浏览器后可删除单个本地会话，账号、OAuth、历史任务与其他账号会话保留。发现同一账号已有 Profile 时复用它；新会话核验到已有 Profile 的账号时提示使用原会话，不重复绑定。错 UID、登录失效、网络核验失败分别显示状态，关闭后的结果仅表示「上次核验」。
- 本阶段仅连接人工交接账号。OAuth 与网页登录身份的可靠关联、多设备 Local Agent、浏览器投稿执行和发布方式选择仍按后续阶段实施。

接口前缀：`/api/workspaces/:workspaceId/accounts/bilibili/browser`。全部要求 `account:manage` 权限，拒绝试用工作室。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /` | 读取本机启用状态和会话列表，不返回路径或 Cookie |
| `POST /open` | `{}` 创建待登录会话；`{ accountId }` 为账号打开或复用会话；`{ sessionId }` 恢复会话 |
| `POST /:id/check` | 核验当前打开浏览器的 UID，并建立或更新账号关联 |
| `POST /:id/close` | 关闭浏览器，保留 Profile |
| `DELETE /:id` | 关闭后删除该会话的本机数据 |

验证：API 的本地浏览器测试覆盖会话隔离与恢复、错 UID、失效与网络异常、进程互斥与旧锁恢复、目录越界、重复 Profile、权限、损坏记录恢复和独立删除；扫码测试另验证本地身份绑定不上传或覆盖 Cookie。使用 ego-browser 和隔离的模拟 API 检查前端新增、核验、关闭、恢复、删除确认、加载失败与重试。真实 B 站扫码及三个真实账号的登录态恢复仍需人工联调，模拟核验不作为真实账号验收。

### OAuth 暂存确认与独立停用（2026-11-28）

本轮先完成可核验的 OAuth 生命周期管理。B 站[官方用户信息接口](https://open.bilibili.com/doc/4/feb66f99-7d87-c206-00e7-d84164cd701c)返回应用内 openid，没有 UID；因此目前仍不把已有网页登录 UID 档案与新 openid 自动合并，也不将用户选择或同名视为身份映射证据。

- 授权从账号详情发起时，将目标账号 ID 绑定到一次性 OAuth state；回调验证用户、工作室、权限、应用 ID 和 state 后核验官方身份，仅加密暂存结果，不创建或覆盖账号。
- `OAuthState.pendingGrantCiphertext` 保存临时 Token、身份、Scope、有效期和应用版本，AAD 绑定工作室、发起用户和 state 记录 ID。待确认窗口沿用 state 的十分钟期限，Token 提前过期时也会清除临时凭据。前端只收到身份、Scope、截止时间与匹配结果。
- 确认时重新核验官方身份、权限和应用版本，在同一事务中消费待确认记录与写入账号。重复确认只有一次能成功，写入失败则回滚消费状态。相同 openid 更新原官方账号，保持原 ID、Cookie 和历史任务；归档身份要求先恢复。
- 所选账号无法与本次 openid 核实时，界面只提供「单独保存官方身份」，保留原档案和任务。首次 UID↔openid 关联仍待可信的平台映射来源，本轮未创建虚假的已验证关联，也未批量移动历史任务。
- 账号详情可查看 Scope、重新发起授权及「停用本系统授权」。停用只移除本系统保存的官方 Token，保留档案、Cookie、本地 Profile 和历史任务；正在提交时拒绝停用。B 站侧的应用授权需由用户到 B 站授权管理中撤销。Cookie 体检不再将官方 OAuth 的授权状态改为 active/expired。
- 迁移：[202611280002_bilibili_oauth_confirmation](../apps/api/prisma/migrations/202611280002_bilibili_oauth_confirmation/migration.sql)，仅增加暂存列及平台/消费状态约束，不移动旧账号和 Token。本机开发数据库已应用该迁移；其他部署需先迁移再加载新 API。

新增接口均位于 `/api/workspaces/:workspaceId/accounts` 下，要求 `account:manage`，拒绝试用工作室：

| 方法与路径 | 用途 |
| --- | --- |
| `POST /bilibili/authorize` | 可传 `{ accountId }`，绑定本次授权目标 |
| `GET /bilibili/pending` | 读取当前用户在当前工作室待确认的官方身份 |
| `POST /bilibili/pending/:id/confirm` | `{ saveSeparately: false }` 只允许同一 openid 的目标档案；`true` 明确单独保存官方身份 |
| `DELETE /bilibili/pending/:id` | 丢弃临时 Token，不创建账号 |
| `POST /:id/oauth/disable` | 停用该官方账号在本系统保存的 OAuth 凭据 |

验证包括 OAuth 单测，以及新建独立 PostgreSQL 测试数据库重放全部迁移后的 26 项业务集成测试；新增集成断言覆盖回调不建账号、跨工作室不能确认、并发确认只成功一次。测试数据库仅由本轮创建并在结束后删除。真实 B 站授权及 UID↔openid 映射仍未完成实测。

### B 站发布方式与任务路由（2026-11-28，第四批）

复用 `TaskPlatformService` 作为发布能力判断入口，按已审版本的内容类型，返回每个账号四种方式的可用性、不可用原因及推荐。推荐顺序为官方 API、本地浏览器辅助、人工交接；沙箱仅供沙箱账号模拟。前端排期不再用账号的接入通道推断本次执行方式。

- `GET /api/workspaces/:workspaceId/tasks/publish-options?variantIds=<逗号分隔的版本 ID>`：要求排期权限，限制版本归属；检查身份、归档、限流、内容策略、OAuth Scope/Token/解密与应用配置、本机 Profile 和未完成任务。专栏与视频按实际 Adapter 能力分别判断，当前官方视频投稿不可用。失效或本系统停用的 OAuth 账号可以主动选择人工交接，账号 ID、接入方式和历史记录保持原样。
- 创建任务可传 `accountModes: { [accountId]: 'official_api' | 'local_browser' | 'manual_handoff' | 'sandbox' }`，必须精确覆盖所选账号。新增可空 `PublishTask.selectedMode`；旧调用和历史任务保持空值并沿用原有路由，显式选择则在创建前完成预检。`executionChannel` 继续记录实际通道。数据库约束所选方式与实际通道的对应关系，并禁止改写已创建任务的方式。该账号与版本已有任务时，选项接口返回 `existingTaskId` 和不可重复发布的原因，界面提供「查看已有任务」。
- Worker 按所选方式路由并再次预检。官方 API 继续走现有提交、租约、平台回读；浏览器辅助与人工交接生成已审交接包，进入 `handed_off` 并释放租约。显式任务同账号有交接待办、待核实或平台处理中的旧任务时不能新建/执行；旧任务也会等待该账号显式任务结束，历史无方式字段的任务维持原兼容行为。
